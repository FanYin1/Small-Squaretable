# P-03 探索主界面：交互讨论稿

日期：2026-10-22（UTC+8）。版本：0.2。状态：已有独立交互示例，七页总体方向已获准作为后续开发参考；本页生产探索能力未实现，最终签收另行记录。

可运行示例与体验路线见 [探索式体验示例](exploration-demo/README.md)，本机端口 5188。两类原创预写剧情用于评审，不代表真实模型、通用状态或长期记忆已经接通。

用户回复“可以”同意继续讨论探索主界面，不表示确认本稿新增的布局、尺寸或操作方式。本稿对应 [决策基线](../product/exploration-experience-baseline.md) 的 DEC-04 至 DEC-09、INV-02/04/05/06/08；参考来源见 [页面研究](exploration-page-proposal.md)。

## 1. 页面任务

用户进入后能理解：我在哪里、刚发生了什么、可以如何参与、行动之后改变了什么。正文负责经历，行动区负责参与，资料窗口负责查看已知事实。

不将即时聊天的长消息列表作为唯一表达，也不将所有资源和工具铺成仪表盘。仍保留原始历史、停止、草稿、费用和恢复能力。

## 2. 桌面布局提案

```text
┌───────────────────────────────────────────────────────────┐
│ ‹ 我的故事     体验名称 · 当前存档          保存状态   设置 │
├──────────────────────────────────┬────────────────────────┤
│ 当前地点 · 在场人物                │ 此次游玩               │
│                                  │ 概况  人物  物品  地图  │
│ 场景叙述                         │                        │
│                                  │ 当前已知状态            │
│ 人物名                           │ 未完成事项              │
│ 「人物的对白。」                  │ 最近确认的变化          │
│                                  │                        │
│ 我的行动与本轮结果                 │ 不显示尚未发现的秘密    │
│                                  │                        │
│ 接下来                           │                        │
│ 查看……                           │                        │
│ 询问……                           │                        │
│ 前往……                           │                        │
│                                  │                        │
│ 或者，描述你想说的话或采取的行动…   │                        │

└──────────────────────────────────┴────────────────────────┘
```

建议在宽屏给资料窗口约 280–340px 的试验宽度，正文使用已有阅读宽度规则；这些数值只供原型比较，不是冻结断点。空间不足时先收起资料窗口，不能挤成难以阅读的窄正文。游玩时不常驻宽平台侧栏。

顶部只保留返回、体验/存档识别、可证实的保存反馈与设置。时间只显示剧情中明确的时间，不使用持续跳动的假时钟。封面或场景图可以作为局部氛围，缺图不影响布局，不要求每轮生成图片。

## 3. 正文与节奏

- 旁白、人物对白、用户行动使用不同的排版层级；人物名清楚可见，不强制每句话配大头像与气泡。
- 每轮呈现当前行动的可感知结果，并在下一处需要参与的位置停下；不连续替用户完成多次决定。长度随情境调整，不将固定字数当作节奏保证。
- 在当前位置提供推荐行动；历史选项作为历史记录，不能误触成为新的提交入口。
- 用户上翻时保持阅读位置，提供“有新进展”入口，不随流式文本强行拉到底部。
- 可点人物名查看已经知道的资料，但不将所有名词都变成装饰性链接。人物资料、观察对象的可操作性必须有明确依据。

## 4. 推荐行动与自由输入

推荐行动按当前情境提供，原型先比较少量候选；数量不固定。表达观察、询问、移动或其他实际意图，避免只有推进主线的单一路径。不要显示尚未实现的成功率、隐藏结果或模型推断成真的信息。

自由输入支持对白、行动和明确询问。先保持一个输入框；Do/Say 等模式是否必要仍属于 OPEN-07，不预先增加必须学习的分类。

OPEN-02 保持未决：

| 方案 | 预期优点 | 需要验证的问题 |
|---|---|---|
| 点击推荐行动直接提交 | 操作直接，接近选择式推进 | 误触、费用预期、用户是否知道会立即生成 |
| 点击填入草稿，再发送 | 便于改写和补充 | 多一步操作是否打断节奏，是否弱化选择感 |

本稿倾向用直接提交作为原型的主要试验方案，同时提供清楚的改写入口；不是用户已确认的行为。不得同时启用两种含糊手势让用户猜测。

无论最终选哪种，提交必须立即反馈并锁住重复提交；生成中显示停止。输入法确认不触发发送。没有选择即发送的隐藏快捷键，也不通过悬停自动生成剧情。

## 5. 资料窗口：查看与行动分开

| 操作 | 提案行为 | 是否推进剧情 |
|---|---|---|
| 打开人物/物品资料 | 展示已保存、允许玩家知道的信息 | 否 |
| 切换地图、放大地图、查看地点说明 | 浏览已有地点与路线 | 否 |
| 点击地图中的地点 | 先展示地点与可执行操作 | 否 |
| 选择前往、使用、交付等动作 | 进入统一行动提交流程 | 是，具体结果由本卡规则决定 |
| 查看最近状态变化 | 展示已确认变化及对应剧情入口 | 否 |

查看既有信息不调用生成模型。需要新的观察或询问时，应明确呈现为行动，遵循实际生成与费用规则。

概况只放当前最相关的少量状态，其余到对应资料页。不预设所有卡都显示体力、好感度、背包或任务；对话型卡可只显示人物与共同经历。

地图没有坐标但有已知地点连接时，可用节点图；仅有地点名称时，用地点列表。缺失关系不能凭想象补成路线。隐藏地点与秘密不提前暴露。

状态变化可轻微提示，例如“新增一条线索”；提示必须基于已确认数据，可以查看来源。未知与加载失败不可显示为 0，不通过持续闪烁吸引注意。

## 6. 一轮交互示例

以下是原创讨论样例，不是首发题材、真实角色卡内容或真实存档。

1. 用户在维修区，看见同伴递来两张记录，推荐行动包含“核对两张记录的时间”。
2. 用户提交该行动，界面立即反馈正在处理；重复点击不会再次提交。
3. 正文说明记录时间存在差异。只有服务端确认发现事件后，线索列表才增加对应记录。
4. 下一轮行动可以围绕追问记录来源或自行描述其他做法展开，不直接替用户作出结论或决定去向。
5. 用户查看线索，只展开已经获得的内容；若决定找当事人询问，那是下一次行动。
6. 刷新后，已确认正文、线索与当前位置一致。失败、停止或状态待核对时，不把未确认变化显示成保存完成。

另一类验证样例使用没有经济或地图的日常关系卡：资料区只呈现人物、已确认的共同经历与约定。相同交互骨架仍需成立，不为凑面板虚构属性。

## 7. 手机与可访问性

- 手机上正文与行动占据主要空间；通过明显的“状态”入口打开资料面板，具体抽屉形态属于 OPEN-03。
- 面板打开后明确返回/关闭，键盘焦点受控；关闭恢复原焦点和阅读位置。
- 推荐行动位于当前剧情末尾，输入区不会同时与展开的资料面板占满屏幕。软键盘、长输入与横屏须真机验证。
- 标签与数值可读，变化不只依赖颜色；菜单、行动和地图中的可选地点可以用键盘操作。
- 保存反馈不持续打断读屏；错误和需要用户处理的状态应能被发现。

## 8. 异常、恢复与纠正

| 状态 | 页面应如何表达 |
|---|---|
| 正文已返回，状态仍待确认 | 分别显示已完成与待核对部分，不统称已保存 |
| 生成中断或用户停止 | 保留已收到内容与真实完成状态，支持核对；不自行决定扣费或虚构结果 |
| 提交结果未知 | 保留输入和请求关联，先核对，不重复生成 |
| 状态同步失败 | 保留最后确认值并标明待同步，不显示新数值冒充成功 |
| 没有可用推荐行动 | 自由输入仍可使用，不能用无来源选项填空 |
| 用户发现错误 | 预留清楚入口；具体改错、重写、回退交互待 OPEN-01 讨论 |

不得把“改一条消息”当作完整历史回退。涉及事件变化时，应同时考虑状态、摘要、记忆和后续内容，这部分需另行确认设计。

## 9. 后续原型应验证什么

- 首屏能否快速辨认当前处境、参与入口和资料窗口。
- 推荐选项与自由输入是否同样容易发现；直接提交/填入草稿的差异是否可理解。
- 查看资料是否被误认为触发行动，地图与物品操作是否清楚。
- 两类不同机制的卡能否使用同一界面，且没有空壳模块。
- 生成、停止、未知结果、状态待确认和恢复是否可辨认。
- 桌面与手机是否保持阅读位置、输入可见性和键盘可操作性。

本稿是 EXP-02 的讨论材料。用户随后要求“给出一个示例”，已据此制作独立交互原型；下一步通过实际体验记录反馈。具体布局和操作仍未签收。
