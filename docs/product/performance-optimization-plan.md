# 项目性能优化方案

更新：2026-11-02。本文定义项目自身的性能优化工作顺序和验收口径。首轮上下文与观测优化、P1角色列表及聊天/故事侧栏切片已随[直接回复版本](../deployment/story-direct-reply-branches-20261102.md#远程部署补充)部署远程；下文各切片“未部署”为首次交付记录。公网资源、健康和匿名页面检查通过，但尚无真实数据库传输量或延迟P50/P95对照，不宣称公网提速；其余阶段仍按下文证据和门槛推进。群聊不在范围内；以单人故事的发现、进入、连续阅读和每轮回复为主路径。

## 首轮已完成

- 普通聊天上下文查询只返回提示词需要的五个消息字段，保留时间顺序；分支路径继续使用分支祖先查询。
- 上下文选择预计算消息 token 成本并复用，冻结的 1、50、200、1000 轮中英混合样本选择摘要不变。
- 记忆抽取每轮只递增计数，达到 5 条阈值时才查询最近 10 条消息，避免每轮重复读取全量历史；原有确认状态过滤保持不变。
- WebSocket 记录不含正文、提示词、令牌或密钥的阶段耗时：历史读取、上下文构建、模型首 token、模型完整生成和整轮处理。
- 本地定向回归 121 项通过，类型检查和服务端构建通过。1000 轮合成历史的上下文选择 P50 从约 56.8ms 降至 38.0ms，P95 从约 78.3ms 降至 57.6ms。该基准只衡量本地 CPU 上下文选择，不包含数据库、网络或模型供应商。

## 目标

- 先找到体验延迟来自浏览器、网络、应用、数据库还是模型，再按证据优化。
- 让列表和首屏加载量有界；故事越长，不应因为读取整段历史而线性拖慢每轮对话。
- 流式回复尽早可见；记忆整理等非必要任务不阻塞用户看到回复。
- 优化不能改变私有数据隔离、故事顺序、规则依据、推荐完整性、记忆来源或计费语义。

## 当前代码基线与待核实项

- 已有 Hono 请求耗时头和超过1秒告警：`src/server/middleware/request-timing.ts`。它提供请求总耗时，不拆解数据库、上下文组装、模型首 token 与完整生成阶段。
- 数据库连接池使用 `DATABASE_POOL_MAX` 配置；健康检查报告配置的池大小，不报告活动/空闲连接、等待队列或查询耗时分布。
- 故事列表仓储支持分页，但 `findByUserId` 接口的分页参数可选；应核对每个调用方都传入上限，避免意外无界读取。
- 消息仓储支持 `before` / `after` 游标读取；普通单人故事生成在 `src/server/routes/websocket.ts` 调用无分页的 `getMessages(chatId)`，仓储会读取该故事全部消息，再进行上下文构造。这是已确认的读取行为；其线上耗时占比仍需测量，其他分支/摘要读取点需分别盘点。
- 前端已经有路由动态导入、Vite手动分包和可选构建体积分析，不能把“新增懒加载”当作从零开始的收益；需确认首屏实际拉取的共享包和动态组件。
- WebSocket 已流式发送回复；目前需测量连接成功率、重连率、首 token 延迟和完整生成耗时，避免把模型慢误判为应用慢。
- 记忆抽取使用持久化任务及重试机制；仍需验证生成响应与记忆任务的资源竞争，以及任务失败时的可见状态。
- 2026-11-01远程主机重启后健康，不能据此推断之前发生过应用性能瓶颈。该次主机重启原因尚未由应用日志证实。

## 指标与观测

先定义一致的采集字段并验证不包含对话内容、提示词、令牌、密钥或完整用户标识。以 request ID、匿名化租户维度、路由、模型内部别名和部署版本关联一次请求。

| 区域 | 记录指标 | 用途 |
| --- | --- | --- |
| 浏览器 | 路由首屏可交互时间、LCP、INP、CLS、JS/CSS体积、图片传输大小、API瀑布耗时 | 区分下载、脚本执行与接口等待 |
| HTTP API | 路由耗时直方图、状态码、响应字节、并发数；P50/P95/P99 | 识别慢接口和长尾 |
| WebSocket | 建连成功率、握手失败分类、断连/重连率、事件发送队列长度、消息处理时长 | 判断对话传输是否退化 |
| 单轮生成 | 排队/鉴权、读取历史、上下文编排、供应商首字节、首 token、总耗时、结束类型、输入输出 token | 分清本地处理慢与供应商慢 |
| PostgreSQL | 查询指纹耗时、调用数、慢查询、池等待/超时、活跃连接、锁等待、缓存命中 | 找到查询瓶颈和连接池压力 |
| 后台任务 | 队列积压、等待时长、运行时长、重试数、失败码、租约过期 | 判断记忆和维护任务是否积压 |

标签使用固定低基数字段。不要使用 user ID、chat ID、角色名或请求 ID 作为指标标签；需要逐请求排查时写入受控结构化日志。对话、提示词和模型原始响应不得进入性能日志。

## 分阶段实施

### P0：建立基线与性能预算

1. 选取内测典型场景：首次发现页、角色库50条、故事存档20条、短对话、长对话（至少200轮）、失败重连、记忆任务积压。
2. 在固定浏览器、视口、网络、数据库数据量和模型条件下各跑多次，报告中位数与P95；冷缓存和热缓存分开记录。供应商调用单独审批和计量，自动化性能回归优先使用受控模型。
3. 记录当前前端构建分块、页面API数量/字节、接口延迟、聊天打开消息数、生成首 token、总耗时和资源占用，形成基线报告。
4. 增加生成阶段耗时埋点及 PostgreSQL 慢查询/连接池观测；确认日志脱敏和采样策略后再部署。

**交付与门槛：**有可复跑脚本与脱敏基线数据；能够把一次慢回复归类到本地阶段或供应商阶段。指标未采到之前，不把猜测写成优化效果。

### P1：压低首屏与列表成本

1. 用浏览器覆盖发现页、我的库、我的故事和聊天页，检查首屏 JS/CSS、字体、图片和请求瀑布。对非首屏管理页按需加载；只有分析产物证明首包包含不必要代码时才调整拆包。
2. 核对所有故事/角色列表均有服务端最大条数、确定性排序和取消过期请求。将 offset 分页作为当前可行方案；仅当数据量或深页查询的测量证实退化时，再迁移游标分页。
3. 列表API只返回页面所需的摘要字段。详情、完整卡片、世界书和编辑数据按需读取；不以列表接口传送完整卡数据。
4. 头像和角色封面生成多尺寸缩略图，优先 WebP/AVIF并保留格式回退；设置合适的 `srcset`、尺寸占位、懒加载和静态资源缓存。先抽样盘点现有上传存量及存储兼容方案。
5. 以网络面板确认请求去重、并行关系和缓存边界。公开不常变列表可评估短 TTL；私人卡片、故事消息、账户余额和运行时模型设置默认不共享缓存。

**验收：**页面/API未发生无界列表读取；首屏不下载非首屏完整卡数据；相同视口、数据与网络下比较 P50/P95、资源总字节和 API 数量，记录改善与无改善页面。图片改造后验证原图兼容、权限和缩略图失败回退。

### P2：控制故事长度对生成的影响

1. 画出单轮生成从消息接收到回复提交的调用图，盘点每个历史读取点及其消费端，区分“供模型使用”“给分支/校验”与“供页面显示”。
2. 统一上下文构造预算：固定系统/卡片设定、最近对话窗口、已确认故事事件、相关记忆和输出保留空间。只从适用的确认消息中提炼记忆；未确认/中断片段不能升级为事实。置顶消息、作者规则、身份、世界书绑定与分支祖先不能因为固定最近N条而丢失；采用按需分页和独立必保留集合，在token预算内确定取舍。
3. 使用索引游标读取需要的消息窗口，避免先取全量再在内存截断。分页加载旧消息按现有稳定顺序补到页面，不能改变回复/分支关系。
4. 对摘要与记忆设定版本、来源消息范围和失效条件。编辑来源、分支或删除消息后重新计算/标记过期；不静默继续使用过时摘要。
5. 将首 token 作为独立目标；回复正文和每轮推荐保持同一条用户可理解的完成语义。记忆抽取/向量化放在回复持久提交后的后台工作，不延迟正文和推荐；队列失败必须保留可重试状态。

**验收：**对短故事与200轮长故事测量，单轮本地历史加载和上下文组装时间不随总历史线性增长；实际发送的消息/token不超过当前模型容量配置；分页、分支、故事恢复及记忆来源回归通过；测试替身与真实模型结果分开报告。

### P3：数据库查询与连接池

1. 从真实流量慢查询和重复查询清单选前三项，不先给所有表加索引。
2. 在代表性数据副本上执行 `EXPLAIN (ANALYZE, BUFFERS)`；比较过滤、排序、租户隔离和分页条件。新索引评估写入成本、磁盘和重复索引，生产新增使用可回滚迁移。
3. 对每个列表固定上限并优化查询形状，避免逐行查询角色/最后消息/计数的 N+1 模式。能批量关联时先用一条批处理查询，再依据计划决定 JOIN 或预聚合。
4. 连接池容量按并发和实例总连接预算配置；监测等待时间、超时和数据库最大连接。不要因 CPU 低或单次健康检查快就盲目扩大池。
5. 检查事务是否覆盖模型网络调用；外部调用不应长时间持有行锁或数据库事务。

**验收：**目标查询的代表性执行计划和耗时有前后对照；连接池等待及超时可观测；迁移在生产数据量级副本演练并有向前/回滚方案。

### P4：并发与后台工作负载

1. 为同一故事的生成、记忆任务和适配工作记录并发、耗时与积压；限制每故事与全局并发，避免大请求耗尽内存/连接池。
2. 增加 `SchedulerService` 单任务不重入、运行时/上次结果可观测及关闭等待。若需要多实例部署，再引入数据库租约/锁；当前单机先不加分布式队列。
3. 记忆 worker 使用现有租约和重试基础，明确最大并发、超时、退避和死信观测；队列积压不能无限占用数据库。
4. 模型请求应用有限超时、取消信号及可恢复错误分类。仅对幂等且明确失败的阶段重试，避免不确定回执造成重复生成或扣费。

**验收：**持续并发测试期间队列、连接池和内存保持在预算内；重试可追踪且无重复故事提交、重复扣费或记忆双写。

### P5：缓存策略与弹性优化

- 等待性能数据确定缓存候选；以键版本/失效规则、租户隔离、TTL、命中率和陈旧窗口一并设计。
- 先评估静态资源CDN和公开发现结果。模型列表已有“进入聊天/打开选择器刷新”的修复，必须保留新增模型及时可见；优先条件请求或配置版本校验，不恢复曾导致列表过期的固定TTL。不能缓存授权响应、私人故事、对话内容、余额或易变的规则状态，除非已有经过验证的隔离与失效机制。
- 仅在单实例指标仍显示应用 CPU/事件循环是瓶颈时，评估 Node 多进程/横向扩容；扩容前先移除进程内调度、内存态锁等单实例假设并验证 WebSocket 粘滞/广播方案。
- SSR、全站缓存、微服务重写和新引入消息中间件不作为当前默认方案；需有基线证据证明收益覆盖维护成本。

## 性能预算与回归门槛

先记录线上基线，再由首轮数据校准目标。建议初始预算如下，均针对受控网络、代表性数据量报告 P50/P95；不是对公网任意设备的绝对承诺。

| 指标 | 初始目标 | 备注 |
| --- | --- | --- |
| 公开发现/列表 API | P95 < 500 ms | 不含图片下载和第三方模型 |
| 私人列表 API | P95 < 500 ms | 记录返回字节、数据条数和冷/热数据库差异 |
| 首屏主要内容可见 | P95 < 2.5 s | 指定桌面/手机视口与网络；另报LCP和JS执行 |
| 聊天历史打开 | P95 < 1.5 s | 初始只读取最近有限消息，旧内容按需分页 |
| 模型首 token | 记录并按供应商分层 | 作为供应商和本地准备阶段分界，不给不同模型共用硬阈值 |
| 后台记忆队列 | 无持续增长；P95等待 < 60 s | 不得阻塞已提交回复 |
| 错误与数据正确性 | 不回退 | 无重复消息/扣费，推荐、分支和来源关系不丢失 |

每个优化提交附基线、测试条件、前后数据和功能回归。若 P95 变差超过10%、错误增加或输出/记忆/计费行为改变，暂停发布并回退对应变更。

## 执行顺序与交付

1. P0 观测与可复跑基线。
2. P1 选择测量证据最强的一个首屏/列表瓶颈，完成实现和两尺寸回归。
3. P2 盘点并消除长故事路径无界历史读取，优先保证上下文与故事语义不变。
4. P3 根据生产查询计划处理前三项数据库瓶颈。
5. P4 处理生成并发与后台任务积压。
6. P5 只对已经证明有效的缓存/扩展方向投资。

每阶段记录工作项、代码版本、受控数据规模、P50/P95和错误/业务回归结果。代码测试通过、部署通过、真实模型体验通过分别记录；不能以构建或静态截图宣布性能优化工作包完成。


## 可复跑的实验条件与发布约束

- 数据集使用自有演示卡，至少覆盖短/长卡、50/200/1000轮历史、置顶消息、分支、未确认片段，以及20/200/2000个故事存档。记录各数据集字节数，不能只按轮数比较。
- 浏览器覆盖1440与390视口，记录设备CPU、网络带宽/延迟、冷/热缓存、构建SHA和测试时间。每种浏览器场景至少20次，报告中位数和尾部样本；API受控测试建议至少200个有效请求才报告P95，P99样本不足时不宣称稳定结论。INP主要由真实交互采样，不能用首次加载时间替代。
- 本地基准和公网链路分开测量；2.5秒首屏目标先在固定10Mbps、100ms RTT、无额外CPU节流条件下评估，同时单独保留真实手机观测。模型供应商时间不计入列表API目标。
- 并发使用独立测试环境，从1/2/4个生成请求逐级观察，再按资源余量扩展。出现持续排队、错误率上升或内存/连接池接近预算即停止；不得在生产上无界加压。
- 付费工程模型预算存在未知回执暂停约束，保持[当前预算状态](engineering-model-test-budget.md)；本方案不自动解除暂停、追加额度或发起真实生成。先完成受控模型性能与正确性检查。
- 长对话渲染测量DOM节点、输入响应和流式Markdown解析开销。若证实逐token全量重排，先合并渲染更新、缓存已完成消息；虚拟列表仅在确有收益时实施，并验证查找、复制、书签定位和阅读位置恢复。
- 新索引先在副本评估，注意并发建索引与事务迁移框架的兼容；取消或失败的索引构建需检查无效索引。新字段和接口优先向后兼容，确保可切回前一镜像。
- 发布单位为能独立测量和回退的一组改动；记录镜像、配置、迁移及基线。先功能回归，再小流量核验，观察同类请求指标。回滚不能覆盖新产生的故事数据，缓存回滚同时处理版本键。
- 本方案归EXP-07D可靠性与性能主线，并与EXP-02页面验收共用证据；关联DEC-29工作台与INV-05/08现有约束。P0至P5是同一方案内部检查点，不以新增编号替代既有工作包完成要求。
