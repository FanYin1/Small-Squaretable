## 大历史检查与分次应用

`backfill:story-memory` 现在按事件版本、任务UUID各200条分页读取。来源正文在数据库计算SHA-256，检查进程仅保留标识、必要元数据与内容指纹；没有把整个长故事加载到命令输出或检查点中。

每次应用最多100个遗漏批次，可用 `--max-jobs 1` 至 `--max-jobs 100` 缩小一次写入量。`jobsToCreate` 是本次计划，`deferredJobs` 是之后仍需补建的完整批次。每次重新只读检查并带新的 `reviewHash` 应用；旧复核结果或更换上限后沿用旧指纹会拒绝。真正不足五轮的尾部进度保留，尚未入队的完整批次仍可由下一次检查发现。

5003轮、超过200万来源字符的合成故事用十次应用补回1000批，无重复来源，保留3轮尾部。当前保守操作上限为每故事10万确认事件、选定角色2万已有任务；超过上限明确拒绝，不能声称支持无界历史。单次锁等待2秒、单SQL15秒仍保留，执行时可能与同故事提交竞争。

## 真实模型验收复现步骤

先在服务器环境配置可用的模型，密钥不进入聊天、报告或仓库。可用性检查命令仅发一次合成短请求，最多32输出token，无自动重试：

```bash
node scripts/story-memory-provider-probe.mjs --config .env.beta
```

这只是服务可用性检查。以下为已完成验收的复现要求；再次执行需计入剩余授权预算，不能将单次阈值视为新增授权：

1. 同卡建立两份故事，约定不同的会面时间/地点/凭证，分别保存表达要求。原文及要求均为合成资料。
2. 每份至少跨越五轮摘要阈值，主故事推进到100轮；在中间触发一次嵌入失败并恢复，保留检查点及来源链。
3. 第50轮备份、还原、重启服务后继续。不要在每轮重复提示早期约定，以免用当前输入掩盖记忆缺失。
4. 返回后询问原约定，检查时地、未完成状态、表达方式和人物边界；另一故事的约定不得进入本故事。记录实际供应商、模型、调用/失败次数、上下文裁剪与采用摘要的证据。
5. 原文事实正确性、文风稳定性、主动权与不泄露分别审阅。自动关键词命中只作为辅助，不能替代语义或体验判断。
