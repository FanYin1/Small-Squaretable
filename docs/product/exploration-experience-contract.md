# 探索体验补全方案：从行动到连续人生

日期：2026-10-22。版本：0.1，讨论与实施输入。

用户指令：“来让我们补齐这几个方面”。本稿承接 [缺口回顾](exploration-gap-review.md)，将九项缺口转为行为、数据边界和验收案例。任务状态仅见 [EXP-02B 及各实施项](backlog.md)，不在这里建立第二套完成率。

**确认边界**：用户已授权补全方案；原有 [DEC / INV](exploration-experience-baseline.md) 继续有效。本文标为“建议”的产品取舍、时序和验收方法是新增提案，不冒充逐条签收；OPEN-01 至 07 不因本文完成而关闭。没有修改生产界面、模型提示词、数据库、计费或运行服务。

## 1. 体验目标如何成为可观察行为

关联 GAP-01 / DEC-01、02、04、08 / INV-10。

“被珍视、被认真回应”落实为：人物注意到玩家说过、做过的事，按照自己的性格作回应；玩家可以影响关系和处境，也可以拒绝。敌对人物可以敌对，伙伴可以不同意，不能把所有角色写成赞美玩家的同一张脸。

| 目标 | 玩家实际看到什么 | 失败信号 |
|---|---|---|
| 成为另一个自己 | 开局知道自己的位置和可参与的事；后续人物按该身份回应 | 只换称呼，背景与关系始终不影响互动 |
| 自主参与 | 自由输入、拒绝、观察、等待都有符合情境的反馈 | 只能沿推荐菜单走；拒绝后仍替玩家执行 |
| 有分量的选择 | 能指认选择改变了哪条信息、约定、资源、人物态度或后续机会 | 不同选择只替换形容词，结果始终一样 |
| 人物可信 | 不同人物的知识、语气、利益与边界有区别 | 人人全知、人人赞同、人人同一种措辞 |
| 连续生活 | 回来后能接上最近处境、未完成事项与表达习惯 | 重新自我介绍，已完成的事重新发生，人物忘记明确约定 |

不要求每轮奖励、每次选择都改数值，也不强制出现任务或好感度。安静地聊天同样可以有意义，其反馈可以是人物记住了一种偏好。

## 2. 叙事推进与行动规则

关联 GAP-02 / DEC-04、05 / INV-02、06、10。建议以“理解意图 → 当前可知回应 → 必要的后果 → 留下参与空间”组织一轮，长度随卡和情境变化，不强制统一段落或选项数量。

| 玩家行为 | 建议处理 | 不应发生 |
|---|---|---|
| 观察、询问 | 提供当前能发现的信息；必要时由人物说明不知道 | 点开地图就自动移动；问价格就自动购买 |
| 明确执行 | 校验位置、资源、规则，叙述尝试及可确认结果 | 仅因用户说“我成功了”就绕过规则 |
| 表达计划 | 记为意向，等实际行动再改位置或物品 | “明天想去港口”立即触发旅行 |
| 拒绝或换话题 | 人物作符合性格的反应，允许新的方向 | 循环弹出同一任务或替玩家接受 |
| 等待、休息 | 有时间规则时按规则推进；无依据时不编造倒计时 | 不论卡类型都扣固定体力或推进一天 |
| 复合行动 | 顺序执行明确且可成立的步骤；遇到新的关键选择停下 | “看看货物再考虑买不买”被理解为已付款 |
| 意图不清 | 先回应确定部分；会改变关键状态的歧义用剧情内短问句澄清 | 每句话都要求二次确认，或擅自推断关键行动 |
| 行动失败 | 给出可知原因和仍能做的事，保留用户自由输入 | 无依据的成功率、强行成功或死循环 |

推进不等于不断给任务。场景可因新信息、人物反应、主动选择或既有时间规则发生变化。建议以收到的行动触发推进；离线期间不默认让世界自行度过数日。明确包含离线模拟的卡须另行声明和实现。

推荐行动应来自当前已知情境和确认状态：有不同意图，不提前泄露秘密，不把结果写成承诺，例如“尝试说服守卫”而非“成功说服守卫并获得钥匙”。过期建议刷新；无可信建议时保留自由输入，不强凑按钮。推荐点击立即执行还是先填草稿仍为 OPEN-02。

**贯穿示例**：林澈说“仓库可能还有一百枚金币”。玩家输入“先别买，问问他消息从哪来”。正文应回应消息来源；面板可以新增“林澈提及仓库金币，未证实”，余额保持不变。若玩家转去休息，林澈可以提醒一次风险，但不能替玩家购买、出发或作承诺。

## 3. 身份：快速开始，也能表达自己

关联 GAP-03 / DEC-01、03、10、13 / INV-01、09、10。建议将卡允许的身份字段显式分成三类：

| 类别 | 例子 | 页面与数据行为 |
|---|---|---|
| 作者固定 | 船长身份、已发生的共同经历 | 展示简短公开说明；不能被普通改名覆盖 |
| 作者提供选择 | 新任/老练船长、两种开局 | 有默认值时可直接开始；仅必要分歧进入开局选择 |
| 用户可自定义 | 称呼、允许范围内的背景、表达习惯 | 折叠在可选调整区；说明限制，不要求填长表 |

旧卡没有字段定义时，不声称自动识别所有可改项：沿用明确的默认人设和既有人设入口，给出能力边界。兼容转换不能把模型猜测当成作者授权。

确认后的身份随本次存档保存，卡和世界书保存明确版本引用或可恢复快照。阅读字号、主题属于账户偏好；虚构身份、约定、经历属于存档。不能因另一张卡里叫过某个名字，就把它当成真实身份传播。

建议开局后，界面别名与剧情身份分开处理：纯列表名称可改；涉及人物记忆的改名、背景和关系变化进入纠正或新开体验设计，不静默覆盖历史。主动改编固定设定应明确为新体验，具体入口仍待设计。

## 4. 状态与记忆：什么可以成为事实

关联 GAP-04 / DEC-06 至 09、11、12 / INV-02、03、04、06、08、09。

### 4.1 按信息类型裁决，避免一个万能优先级

| 信息类型 | 示例 | 建议写入位置与权限 |
|---|---|---|
| 设定与规则 | “本世界没有魔法” | 已绑定且锁定版本的内容配置；闲聊不能覆盖 |
| 已确认事件 | 交易完成、交出钥匙 | 通过规则和版本校验后形成事件并更新状态 |
| 人物主张 | “仓库有金币” | 带说话人和来源的见闻；不是资产证明 |
| 玩家意图 | “我打算明天过去” | 意向/待办；不当作已执行动作 |
| 推断与未知 | “也许守卫在撒谎” | 标记推测或未知；不升级为世界真相 |
| 表达偏好 | “少用华丽比喻” | 本次体验的风格约定；不改人物性格或世界事实 |

模型可以提出事件候选；服务端按字段类型、来源、动作权限、前置条件和状态版本裁决。对于数值资源，不能把任意模型输出当成可执行补丁；对于没有确定规则的叙事卡，允许记录有来源的叙事事件，但须承认其语义判断仍依赖模型与体验验证。

面板每项至少能回答：值是什么、何时确认、来自何处、谁可见。未知不是零；未发现不是不存在。保留发生过的旧事件，当前状态由有效事件推导；承诺改期是新增调整事实，不删除原约定。

### 4.2 正文、面板与冲突

建议对会改变关键状态的轮次，正文流式阶段标明本轮仍在生成或确认；完成时与事件、状态版本一起确认。流式文字可能先出现矛盾，因此不能仅靠最终抽取补丁来掩盖问题。

发生矛盾时：保留最后确认的状态，把候选轮次标为未确认，解释“这一轮的结果尚未确认”；阻止基于它继续推进，允许阅读旧内容和编辑草稿。内部可按原请求做有界重校验；不能静默把已经展示的正文换成另一段。若无法安全恢复，进入显式错误处理；如何重写已确认历史仍属于 OPEN-01。

### 4.3 长期连续性建议

建议将持久数据分为：原始轮次与事件、当前状态、带来源的经历/约定、可重建摘要与检索索引、存档内表达约定。摘要和向量记录是派生材料，不能成为资产或事实的唯一依据。

每轮优先获得固定规则、当前关键状态、相关未完成约定、人物允许知道的信息、相关经历和最近对话。预算不够时先压缩或减少派生摘要；关键状态或必要规则仍放不下时应报告能力限制，不静默遗漏后继续编造。

查询、写入、相似去重、合并、清理均必须携带用户/租户与存档作用域。人物知情范围单独过滤：玩家读到某条信息不意味着所有 NPC 都知道。表达约定保存用户明确表达的内容，不把一句抱怨推断成永久人格。具体表结构、检索策略和摘要频率仍由 OPEN-04 设计与测试收敛。

## 5. 生成等待、失败与消费

关联 GAP-05 / DEC-05、07、08 / INV-02、05、08。以下为建议时序，不是已经实现的事务协议或新价格方案。

1. 接收输入：固定请求 ID、存档、状态版本与身份；服务端校验权限和消费前提。客户端显示已接收须以服务端确认为据。
2. 生成回应：显示真实生成状态，允许停止；流式正文仍可能未确认。
3. 确认结果：校验候选事件、正文一致性与状态版本，在短事务中确认对应的持久记录。不能在长数据库事务中等待模型。
4. 恢复结算：账本与轮次结果通过同一请求可追溯，明确处理中/已结算/待核对；“进度已保存”和“费用已结算”分开。
5. 更新派生记忆：可靠入队，可去重重试；失败时用已确认事实与近期原文恢复必要上下文，不因摘要失败重复整轮生成。

| 故障 | 正文/状态 | 用户可做什么与费用原则 |
|---|---|---|
| 请求尚未受理即拒绝 | 保留输入，不新增确认事件 | 修正前提后重试；服务端确认无调用才能显示未消耗 |
| 生成中失败或用户停止 | 部分正文标为未完成，候选状态不提交 | 查看已保留内容、编辑草稿；已有模型消耗按真实账本处理 |
| 状态解析/校验失败 | 不显示保存成功，不将未确认结果用于下一轮 | 查询/恢复同一请求；不得无提示启动第二次付费生成 |
| 版本冲突 | 保留草稿，展示服务端最新确认版本 | 先核对新进展，再由用户决定是否重新行动 |
| 已提交但确认回包丢失 | 结果未知，不等于失败 | 查询原请求，恢复既有结果，禁止盲目重发 |
| 派生摘要/索引失败 | 已确认事件与状态保持有效 | 后台重试；必要信息不可恢复时解释限制 |

停止与完成同时发生时，以服务端终态为准；不能承诺点击停止一定撤销已确认结果。

建议不把系统内部修复、重复投递或可选推荐失败记成用户再次行动；现有供应商成本与用户扣点需分开审计。是否收费及失败费用口径沿用已公布规则；若新增调用改变用户计费，应先形成明确变更方案。此文不承诺所有失败免费。

推荐生成失败可以降级为自由输入；关键状态确认失败不能降级成“假装成功”。读取资料和地图不触发剧情生成或扣点。

测量至少分开记录：受理到首段文字、正文完成、关键状态确认、派生记忆完成、每轮调用次数和实际用量；按模型、卡类型、上下文长度记录成功与失败。数值目标待真实试跑确定，不编造已达成的延迟指标；超时、最大重试次数和成本上限须在接入前给出可配置边界并验证。

## 6. 存档的完整生命周期

关联 GAP-06 / DEC-07、08 / INV-01、02、09。建议首批明确以下行为：

| 操作/情境 | 建议行为 |
|---|---|
| 继续 | 进入指定存档，恢复确认进度、未完成请求及草稿，不自动新增一轮 |
| 同卡再开一次 | 显式创建新存档，保留旧存档；两者身份、事件、记忆隔离 |
| 重命名 | 只改列表名称，不能改变玩家的剧情身份 |
| 归档 | 从活动列表隐藏，可恢复；不等于删除，不影响记忆隔离 |
| 删除 | 说明范围，终止或隔离在途写入；删除相关数据而非仅隐藏会话 |
| 生成时离开 | 建议已受理请求继续处理；返回查询原请求。关闭网页不视为停止，也不保证服务故障下仍能完成 |
| 多标签/设备 | 建议同一存档同时只有一轮可推进；其他页面可读，旧版本提交被拒绝并保留输入 |
| 卡或世界书更新 | 已有存档继续使用固定版本；新存档使用所选新版本，迁移另议 |
| 卡被移除/权限变化 | 重新检查访问权限，区分能否读历史、能否继续、能否新建；不靠客户端快照绕过服务端策略 |

“删除”“归档”“生成中离开”属于新增具体交互建议，需与现有 API 能力核对后实现。不能把现有演示的一卡一份本地进度等同于该生命周期。

## 7. 代表内容与体验验收

关联 GAP-01、07 / DEC-02 至 08 / INV-01 至 10。建议先做四类小型验证样本，可原创或使用许可清晰的内容；这不是首发卡数量或商业内容定案。

| 样本类型 | 主要验证 |
|---|---|
| 人物/日常 | 性格、偏好、承诺和慢节奏；没有地图或余额仍成立 |
| 世界主持/探索 | 地点、线索、发现范围；只读地图与移动区分 |
| 多人物 | 不同知识与利益、私下谈话不会自动传播 |
| 有资源规则 | 物品、购买、资源不足、失败与状态一致性 |

先用受控模型输出验证协议和故障，再用真实模型自由输入验证体验。两张预写演示保留用于视觉回归；不能用其固定分支证明模型质量。第三方导入能力仍按 EXP-03B 分层验证，不运行未知作者脚本来证明兼容。

| 用例 | 操作 | 可判定的通过证据 |
|---|---|---|
| EX-01 拒绝 | 拒绝当前推荐，改为休息 | 无被拒绝行动的事件；人物合理回应，有可继续空间 |
| EX-02 否定与复合意图 | “先别买，问价后再考虑” | 回应价格；无交易或扣款事件 |
| EX-03 传闻 | NPC 提及金币 | 见闻有来源；余额不因主张增加 |
| EX-04 自由行动 | 输入未列在推荐里的合理行动 | 进入同一请求与状态链路，不回落为固定模板 |
| EX-05 人物知情 | 只向一个人物透露秘密 | 另一人物的回应和面板不泄露该秘密 |
| EX-06 后果 | 在两个隔离存档中作不同有效选择 | 指认合理的事实/信息/关系后果差异，不要求固定文案 |
| EX-07 约定与风格 | 约定会面，明确偏好，推进并触发摘要后返回 | 原约定可追溯；时间和表达连贯，无重复承诺或泄露 |
| EX-08 来源与查看 | 打开地图/状态并查看来源 | 来源真实可达；查看不移动、不生成、不扣点 |
| EX-09 失败恢复 | 分别注入中断、校验失败、提交回包丢失 | 无重复事件/扣点，未确认不显示已保存 |
| EX-10 并发隔离 | 同卡双存档、双标签提交，切账号接收迟到结果 | 无跨档/跨账号写入，版本冲突可恢复 |
| EX-11 内容版本 | 更新绑定世界书后继续旧档 | 旧档使用原版本；新档版本明确 |
| EX-12 生命周期 | 导出、删除、恢复测试备份，再尝试检索/续写 | 数据关联完整；已删除内容不会被派生记忆或任务重新带回 |
| EX-13 入口中断 | 登录/邀请码/余额/缺依赖/失效卡/保存错误 | 原选择及草稿可恢复，错误不被显示成空状态 |

每次真实体验记录：样本和配置版本、模型标识、完整测试输入、预期约束、实际行为与关键来源、失败归因。使用合成测试内容，不把真实用户聊天放进文档。主观质量单列人工评审，不由字符串匹配替代。

建议将越权泄露、跨存档污染、重复资产/扣费、虚假保存、替玩家作关键决定列为不可接受的失败；遇到这些应修复后复测。自然度、推进节奏、人物辨识度与自由输入质量分别记录例子和问题，不用平均分掩盖硬性失败。重复试跑与样本数量在真实模型评测开始前登记，不事后挑选一次成功结果。

## 8. 页面全流程与数据生命周期

关联 GAP-08、09 / DEC-03、06、07、08、14 / INV-01、05、06、08。

### 8.1 页面与状态矩阵

| 页面 | 在正常效果之外补齐 | 关键行为 |
|---|---|---|
| 发现/详情 | 加载、空、搜索失败、内容失效、依赖缺失 | 不把失败当无内容；明确为何不能开始 |
| 认证/必要开局 | 未登录、邀请码、身份冲突、创建超时 | 保留所选卡、合法回跳和输入，复用既有建号/创建能力 |
| 游玩 | 生成、停止、未确认、连接断开、余额不足、并发 | 正文可读，草稿可保留；结果与费用状态分开 |
| 我的故事 | 首次为空、列表失败、恢复中、多个同卡档、归档 | 继续明确指向存档；无摘要用真实摘录 |
| 创作 | 本地草稿、保存中、保存失败、缺依赖、无发布权限 | 不把预览当发布，不把本地草稿当服务端保存 |
| 我的/账户 | 未认证、余额读取失败、结算待核对、退出登录 | 不伪造余额；退出后清理可访问的旧用户缓存 |

沿用已保存的七页视觉参考，扩展这些状态，避免异常路径重新出现另一套界面。逐页验证明暗主题、桌面与手机、键盘操作、缩放、大字号和弱网；真机输入法、软键盘、屏幕阅读器单列证据，截图不能替代。本文不另建一套视觉令牌。

### 8.2 新数据必须纳入既有管理能力

| 数据 | 建议的导出、删除与恢复要求 |
|---|---|
| 身份、配置版本、原文、事件、状态 | 明确所属存档；恢复时一并校验引用和版本。卡原始内容的导出遵守内容权限，不从玩家导出接口泄露隐藏设定 |
| 摘要、向量、人物记忆 | 标明派生和来源；导出按权限呈现，删除同步清理；允许从合法来源重建，不能复活已删除源 |
| 缓存、草稿、后台队列 | 退出/删除后失效；在途工作提交前再次检查存档存续和权限，防止删除后回写 |
| 账本与必要审计 | 与故事正文分离；按既有明确的保留策略处理，不宣称删除故事等于抹除全部交易记录 |
| 备份 | 记录覆盖数据、恢复步骤和保留周期；删除不是瞬间擦除历史备份，恢复后必须重放删除标记或等效清理再开放访问 |

导出用于玩家阅读和用于管理员迁移的范围不同，二者不能共用一个“全部数据”接口。备份恢复验证应覆盖数据库、依赖版本、索引重建和删除约束，不只验证消息条数。具体留存期限不在本稿虚构，实施时记录实际配置与用户可见说明。

## 9. 纠正边界与后续实施顺序

错误纠正已登记为 OPEN-01，本次补充讨论结构，不默认为已批准的功能：

| 用户想做什么 | 必须讨论的影响 |
|---|---|
| 修正笔误/称呼 | 是否仅修展示；语义一旦变化不能假定状态不受影响 |
| 指出系统记错 | 依据哪条原文/规则裁决；涉及哪些事件、摘要和后续记忆 |
| 换一种表达 | 是否保持同一事件结果，怎样验证不夹带状态变化 |
| 改变过去选择 | 从何处形成新分支、保留什么历史、后续状态与费用如何处理 |

建议首批至少能定位来源和报告不一致，为后续裁决保留版本依据；在纠正方式确认前，不通过编辑文本按钮直接重写已确认的状态或自动删除后续内容。

| 工作包 | 本稿提供的输入 | 对应证据 |
|---|---|---|
| EXP-07A | 默认身份、继续/另开、入口异常 | EX-10、13 与四页视觉对照 |
| EXP-03A/04A | 规则版本、信息类型、裁决、可见范围、持久化 | EX-02、03、05、08、09、11 |
| EXP-04B/07B | 叙事边界、自由行动、推荐、生成与消费状态 | EX-01、04、06、09 与真实阅读页 |
| EXP-05A | 事实/派生区分、约定、风格、恢复与全链路隔离 | EX-07、10、12 |
| EXP-03B/07C | 代表卡、依赖诊断、创作和账户异常 | 分层兼容记录、EX-11、13 |
| EXP-07D | 全入口矩阵、数据恢复、逐页实际效果 | EX-01 至 13 分开记录自动化、模型、人工与真机证据 |
| EXP-06 | 纠正分层及状态影响 | 先明确行为，之后补专用验收，不用当前 EX 冒充已覆盖 |

建议先做一条真实服务端链路：选卡 → 默认身份开始 → 自由/推荐行动 → 人物回应 → 可追溯状态 → 离开恢复。必须包含拒绝、否定、未知事实和失败，不能只跑最顺利的固定分支；随后增加同卡第二存档及第二种机制的卡，验证通用性，再扩展其余页面和导入兼容。

这补充原实施计划的验证顺序；EXP-07A 无依赖工作仍可推进，不把所有讨论细节变成前端启动条件。发布仍以本机内测候选为范围，原型、正式实现、部署与用户签收各自记账。
