# 交易与奖励的分支来源校验

对应DEC-20/21及INV-01/08/09，属于AD-3交易执行链和EXP-06分支恢复的有限工程修复。没有完成第三方卡片的完整交易适配，也不关闭EXP-ADAPT或EXP-06。

## 实际效果与根因

此前重放核验规则可用性、事件变化和当前状态，却只根据事件的行动编号执行；自由输入确认也没有检查原始提案和输入证据。因此即使历史用户输入被改成拒绝或问价，数值仍一致时也能重放扣款。

现在推荐行动必须匹配当时冻结规则的完整标签或别名；“先别支付”“询问价格”不能成为扣款来源。自由输入确认必须来自紧邻的原始待确认提案，版本、原文和确认内容一致，行动证据包含在原文中。多项行动按原顺序重放，全部付款、所得、奖励及领取记录一致后才能建立分支。

提案、行动或来源有缺口时返回`STORY_PREFIX_UNAVAILABLE`，不补造历史或回写原档。有效旧档仍可预览、建立分支和再次分叉；不完整的历史需要保留原档并核对来源，不会自动迁移成有效交易。

## 复现与隔离验证

先增加回归用例，旧实现出现4项失败：三种非执行输入仍允许交易重放，以及错误确认类型仍通过。修复后3个定向文件共62项通过，覆盖输入、别名、原提案缺失/修改、证据、版本、确认类型、复合行动和既有恢复边界。类型检查及定向ESLint通过。

新增`node scripts/exploration-entry-check.mjs --transactions`专项，使用临时数据库、本地受控回复和明确标注的测试规则，不依赖群聊专项。5组通过：

1. 支付20枚与获得1张票同时持久化；重试不重复扣款，达到票券容量后拒绝再次购买。
2. 购买加一次性奖励遇到数据库故障时，消息、事件、状态全部回滚；恢复后重试成功，连续两次分支保留付款、所得、奖励领取记录及原提案证明。
3. 待确认提案、中断确认和明确拒绝均不扣款或发奖励；中断后旧提案不能再次确认。
4. 故障注入修改输入或提案后，即使资源总量保持一致，预览和创建仍返回409；不留下分支或创建请求占位，不修改原状态。恢复原始证据后可重新预览。
5. 重启API进程后证明仍有效；1440和390宽度浏览器均能预览从初始余额100重新开始，不继承未来余额85。浏览器异常0，保存2张截图。

基础HTTP/WebSocket冒烟同时通过。第三方原卡没有在这组检查中生成剧情；这些测试规则只验证执行和恢复链，不能作为原卡机制适配证据。首次运行因Drizzle把故障注入异常包装在`cause`内而导致测试断言失败；改为核对确切的底层错误后完整重跑通过，没有放宽状态回滚断言。失败日志与最终通过日志均保留。
