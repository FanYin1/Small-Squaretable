第二轮边界：草稿不上传服务端、不跨设备同步，关闭标签页后不保证保留；存储不可用时提示用户并保留当前组件内存输入。WebSocket 通过 `clientMessageId` 回传匹配本次发送，避免另一设备同文消息清空草稿；这是确认关联，不是服务端幂等或自动重试。断线后未收到确认的草稿会保留，恢复提示要求先核对正文，不自动重发。客户端与服务端需同步部署；旧服务端不回传标识时保守保留草稿。开场保存后的迟到响应也不会写入另一个故事。

此前验证记录：相关测试共 129 项通过；类型检查、前端构建、补丁格式检查通过；lint 0 error / 267 条 warning。隔离 Chromium 使用 mock API 验证暗色下 1440×1000、390×844 的草稿刷新恢复、上滑阅读不受流式更新打断、新剧情按钮可见且返回最新、输入可见性和横向溢出，页面脚本无错误；第一轮另有浅色布局验证。以上不等同真实模型、结算或手机软键盘验收。

前轮重试安全补强（2026-10-21）：前后端仅依据整轮结束事件中的 `retryable: true` 开放重试，错误事件本身不解除正在执行的请求锁定。重试保留草稿确认回调并防止连点；对账仅按消息 ID / 请求标识关联，另一设备同文消息不清空当前草稿，重复回包不重复插入。该轮 4 个相关测试文件共 95 项通过，类型检查通过；当时尚未解决多实例首次并发写入。

本轮持久化请求补强（2026-10-21）：新增 `generation_requests`，以故事和请求标识的唯一键原子争取执行权，记录接受、运行、完成、停止或失败以及关联用户消息；正文和指定角色列表参与请求摘要。同一请求在其他实例已接受、终态或删除用户消息后都不能重新执行；重复提交的结束事件不再广播到整个故事。真实 PostgreSQL 两连接池 40 并发只有一个获胜者，17 项检查通过。未向业务库应用迁移；上线前须完成 0040 并升级全部 WebSocket 节点。详见 [`generation-requests.md`](../deployment/generation-requests.md)。

当前边界：同标识执行权已持久化，但消息、模型调用和点数结算不是同一原子事务；进程退出遗留记录不自动接管。跨实例实时状态、停止控制、不同请求的故事串行化、重连补拉分页、异常部分正文恢复与真实模型结算验证继续保留在后续清单中。

本轮验证：4 个相关测试文件共 107 项通过；一次性 PostgreSQL 库 17 项检查通过并已清理；类型检查、生产构建和补丁格式检查通过；定向 lint 0 error / 3 条既有 warning。没有执行真实模型、真实结算或多节点浏览器联调。

详情页第一版验证（2026-10-21）：详情与聊天路由 18 项测试通过，类型检查、前端构建与定向 lint 通过。隔离 Chromium 使用 mock API 检查暗色 / 浅色的 1440×1000 与 390×844，长标题、长标签、坏封面回退、余额显示、44px 进入按钮和无横向溢出均通过；浏览详情不创建聊天、不发起模型调用，页面无脚本异常。余额通过真实 API 接口读取，此次浏览器数据为模拟值；没有验证真实结算。ST-02 发现页与 ST-04 身份确认继续待办。

实现顺序允许先用已有会话落地 ST-05 的阅读骨架；完整 ST-05 验收仍依赖 ST-04 的身份与开场体验。总清单中的 UX-1 保持未完成。

用户登录后可以完成这条闭环：

1. 在发现页看到适合自己的故事和继续入口。
2. 打开故事详情，理解题材、角色关系、开场情境和点数规则。
3. 确认自己的名字与身份后进入故事。
4. 在阅读页看到连续剧情、自己的行动和角色回应。
5. 生成中可以停止，失败后可以重试，刷新或断线后可以恢复。
6. 每次生成后的消耗清楚可见，余额不足时能理解原因并进入余额页。
7. 桌面端和手机端都能完成上述流程。

第一版暂不包含：多人实时共写、复杂分支树编辑器、在线支付、音频剧场、自动生成封面、完整的作者收益系统。这些功能会增加状态、成本和内容审核面，先放入后续评估。

- **验收**：用户能展开查看消耗拆分；关闭或减少长记忆时能看到明确的预期变化；文案不承诺固定价格；没有 token 数量时不展示猜测值。
- **估时**：1.5 天

### 阶段 4：作者交付与内容质量

#### ST-11 故事元数据编辑

- **优先级**：P1
- **依赖**：ST-02、现有角色编辑 / 发布流程
- **范围**：在现有角色编辑能力上补齐故事标题、情境钩子、开场片段、角色关系、题材标签、内容边界和封面焦点；作者预览必须使用与用户阅读页一致的视觉。
- **涉及**：`CharacterEditor.vue`、`CharacterPublishForm.vue`、`CharacterPreview.vue`、服务端 schema 与发布校验。
- **验收**：作者可以预览发现卡、详情页和开场；缺少必要字段时不能发布；标签数量和长度有服务端校验；NSFW / 年龄 / 审核规则沿用现有服务端判断；编辑保存失败时保留草稿。
- **估时**：2 天

#### ST-12 首次使用引导

- **优先级**：P2
- **依赖**：ST-02、ST-05、ST-09
- **范围**：新用户用三步以内理解发现、身份和行动；可跳过；回访用户不重复打断；引导内容使用真实界面而不是独立教程页。
- **验收**：新用户不看文档可以开始第一段故事；跳过状态持久化；键盘和手机端可完成；引导不会覆盖输入框、余额提示或错误提示。
- **估时**：1 天

### 阶段 5：响应式、可访问性和发布质量

#### ST-13 响应式与无障碍验收

- **优先级**：P0
- **依赖**：ST-02 至 ST-09
- **范围**：按 480 / 768 / 1024px 断点验证发现、详情、身份弹层和阅读页；覆盖安全区、软键盘、触控目标、键盘操作和屏幕阅读器名称。
- **验收**：390×844、768×1024、1440×1000 三种尺寸均可完成主流程；触控目标不小于 44×44px；焦点顺序合理；弹层支持 Escape；正文、错误、费用和状态不只靠颜色传达；横屏输入区仍可见。
- **估时**：2 天

#### ST-14 自动化测试与视觉回归

- **Beta 验证**：最新证据见文首发布收口；mock 回归与真实后端的受控模型验收分开记录，均不代表真实供应商已通过。
- **优先级**：P0
- **依赖**：ST-13
- **范围**：为关键交互补单元 / 组件测试，并用 Playwright 覆盖发现 → 详情 → 身份 → 阅读 → 发送 → 停止 / 失败 / 恢复；生成暗色、浅色、移动端截图。
- **验收**：关键流程在 mock API 下稳定通过；不会依赖真实 Postgres、Redis、模型或支付；浏览器控制台无错误；`vue-tsc`、lint、相关 Vitest 和 E2E 通过；截图差异有人工结论。
- **估时**：2 天

#### ST-15 上线检查与文档收口

- **Beta 交付**：新增 [`部署与运营说明`](../deployment/beta-release.md)，全新安装与存量升级明确区分，公网发布门槛保留未完成。
- **优先级**：P1
- **依赖**：ST-14、P3-1、P3-2
- **范围**：更新产品定位、视觉语言、待办状态、环境变量说明、运营手册和用户可见的点数规则；确认演示页与生产页面不会被误认为同一实现。
- **验收**：新开发者能按文档启动、登录、创建故事和测试生成；生产环境关闭演示占位；点数、年龄、NSFW、邀请码、平台熔断和断线恢复的说明与实际行为一致。
- **估时**：0.5 天

## 四、推荐里程碑

| 里程碑 | 任务 | 用户可见结果 |
|---|---|---|
| M0 视觉落地 | ST-00、ST-01 | 生产页面具备确定的视觉基础和路由边界 |
| M1 可以开始故事 | ST-02、ST-03、ST-04、ST-05 | 用户能发现故事、确认身份并进入阅读页 |
| M2 可以稳定互动 | ST-06、ST-07、ST-08、ST-13 | 用户能发送行动、停止生成、断线恢复并在手机上使用 |
| M3 可以透明交付 | ST-09、ST-10、ST-15 | 用户理解消耗，运营者能解释余额与流水 |
| M4 可以持续供给 | ST-11、ST-12、ST-14 | 作者能交付高质量故事，新用户能快速开始 |

建议第一轮开发顺序为：`ST-00 → ST-01 → ST-05 → ST-07 → ST-08 → ST-02 → ST-03 → ST-04 → ST-06 → ST-09 → ST-13 → ST-14`。这样先把最有风险的真实聊天阅读链路跑通，再补发现页和作者交付，不会先做出一个漂亮但不能稳定生成的目录。

## 五、每个任务的开发纪律

- 先写接口输入、输出、加载、空态、错误和恢复行为，再写视觉样式。
- 生产页面不复制演示页的本地状态；余额、生成状态、消息和权限以服务端结果为准。
- 不为了做故事体验重新发明角色、聊天、人设、点数和 WebSocket 数据模型；先验证现有接口是否够用。
- 新增接口必须同时补权限、幂等、分页 / 游标、错误码、审计需求和测试，不只做成功路径。
- 每完成一项，更新本清单的验收结论，并附测试命令和浏览器验证尺寸。
- 发现与故事无关的存量问题时单独登记，不混入当前任务，避免视觉改造变成大范围重写。

## 六、开工前的第一批具体动作

1. 执行 ST-00：画出当前 `Market → CharacterDetail → Chat` 与演示 `Discover → Detail → Reader` 的映射。
2. 执行 ST-01：从 `variables.css` 和现有组件中清点颜色、字体、按钮、弹层和输入令牌。
3. 执行 ST-05：先改造 `ChatWindow.vue` 的阅读布局，并保留现有 WebSocket 发送逻辑。
4. 执行 ST-07：补生成状态机和停止 / 重试测试，再接入视觉状态。
5. 执行 ST-08：先修复直接打开 `/chat/:chatId` 的会话恢复，再做发现页继续入口。

完成这五步后，项目就有一个可真实使用的互动故事阅读骨架，后续工作可以按本清单逐项交付。
