## 用户行为与改动原因

后续分批摘要（2026-10-24）：检查点现可同时保存版本化事实与摘要，成功且来源有效的批次可参与有界续写；旧事实数组仍兼容且不补造摘要。见 [摘要生命周期与独立验证](story-summary-lifecycle.md)。不新增迁移，未部署3081；下方原始验证数字保留，不代表全局滚动摘要已完成。

已保存的故事回复不会因为辅助记忆抽取失败而被判成失败。此后继续同一故事，后续提示可检索已经完成派生的记忆；重启后继续累计尚未满批的回复，恢复失败任务。不同故事、同一群聊中的不同角色分别处理。

旧链路依赖进程内计数，每五次回复先清零再抽取；抽取错误被转换成空数组，嵌入不可用时可能返回零向量。重启或服务故障会丢失处理进度，且没有足够信息区分“本轮没有重要内容”和“没有成功处理”。

新链路适用于 `content_snapshot_version = 1` 的故事，包括原生规则单卡与普通叙事单卡/群聊。无内容快照的旧聊天继续旧链路。迁移只收集迁移后新提交的确认事件，不扫描旧历史、不自动重做以前的抽取、不为未标记的旧片段猜测完成状态。部署时必须明确这一覆盖起点。

## 处理流程与一致性

1. `story_events` 插入确认事件时，数据库触发器在同一事务将来源加入 `story_memory_progress`。每个故事、角色累计五个确认事件后创建一个 `story_memory_jobs`，并清空这批进度。停止片段不计入；提交回滚同时回滚计数和任务，幂等重放不会重复插入事件。
2. 调度器每15秒领取一个到期任务。同一进程不重叠执行；不同进程通过行锁、`SKIP LOCKED` 和租约令牌竞争。领取增加尝试次数；租约到期后可重领，达到上限的任务转为 `failed`。降低配置上限也会收敛已经耗尽预算的排队任务。
3. 抽取只读取该批事件对应的五组完整输入/回复。校验故事、角色、角色类型、确认标记、事件版本与请求号；中止片段、缺失来源或不匹配来源不调用模型。源 JSON 超过字符预算时显式失败，不截断原文后宣称完整。
4. 模型必须返回有类型、内容和原文消息 ID 的数组，最多12项、每类最多3项。引用不在本批来源内、字段格式错误等属于失败；只有有效的空数组代表没有可提取内容。提示要求区分传闻、意图、已发生事实，不能用该提示替代语义正确性验收。
5. 通过校验的抽取结果和来源摘要先保存到任务。嵌入失败或进程在此后重启，可以复用检查点，不必重新请求抽取。严格嵌入接口每次实际请求服务，不沿用启动时的离线判定；缺维度、非有限值、数量不符或全零向量全部拒绝。
6. 最终事务重新核对来源摘要、租约和当前任务，按故事范围做精确内容去重，写入记忆、非零向量、`story_memory_links` 的事件/消息依据及任务成功状态。任一写入失败全部回滚。旧工作进程不能在租约被替换后提交；原文变化后不能提交旧摘要。
7. 同故事重复文本复用记忆记录与来源链接，不做可能误合并事实的语义改写；维持此前自动抽取使用的免费档记忆上限，淘汰时向量及链接级联清理。没有改变用户订阅与计费规则。

少于五次确认回复的进度仍会保存，但暂不触发抽取，也没有“离开即强制抽取”。原文、确认状态、最近事件和人工风格笔记原有保存方式继续生效。后台抽取没有新增前端“已完成”提示，任务成功不能冒充玩家已经看过或确认其内容。

## 资源预算与重试

| 配置 | 默认值 | 边界 |
|---|---|---|
| `STORY_MEMORY_JOBS_ENABLED` | `true` | `false` 暂停消费，仍保存进度/任务；新故事不回退到旧抽取链路 |
| `STORY_MEMORY_MAX_ATTEMPTS` | `3` | 每轮自动处理1–5次；崩溃后重领也计次 |
| `STORY_MEMORY_TIMEOUT_MS` | `30000` | 抽取和嵌入各有独立中止信号，允许1000–60000毫秒 |
| `STORY_MEMORY_MAX_INPUT_CHARS` | `24000` | 完整来源 JSON 字符数，允许1000–48000；不是精确token预算 |

默认重试等待15秒、30秒，由调度周期继续领取。租约长度为两次调用预算加60秒。每次领取最多调用一次抽取模型，禁用该调用内部的额外重试，模型输出上限2000 token；有抽取检查点时只重试嵌入/入库。模型调用沿用平台支出计量和熔断，不新增玩家扣费。进程在模型响应后、检查点提交前崩溃，仍可能产生一次重复的外部调用；不能承诺供应商侧恰好调用一次。

任务失败码持久保存，调度入口对本次 `retry` / `failed` 报错；不把正文、模型响应或服务密钥写进错误字段。每个工作进程每次调度处理一个任务，尚无跨实例的全局吞吐配额。没有配置可用模型或嵌入服务时，任务会达到上限并保留，不能把排队或失败状态称作长期记忆完成。

## 受控重放

若问题是确认历史从未入队或未满批进度遗漏，使用 [独立补建工具](story-memory-backfill.md) 先只读检查、再以复核指纹应用。它保留所有已有任务，包括失败任务；本节重放仍负责已有失败批次。两条路径都不自动升级无确认依据的旧聊天，均未对3081运行。

先修复供应商、嵌入、数据库或预算问题，再由运维查看具体任务。工具使用显式提供的 `DATABASE_URL`，不自动读取候选环境文件，也不会输出故事正文。默认命令只读：

```bash
npm run retry:story-memory -- --job <任务UUID>
```

核对返回的 `status`、`attempts`、`error_code`、`has_checkpoint`、`replays`；仅在确认需要重新处理后执行，例如看到失败任务的 `attempts` 为3：

```bash
npm run retry:story-memory -- --job <任务UUID> --expected-attempts 3 --apply
```

只有仍为 `failed` 且尝试次数匹配的任务才能重放；运行中、已成功或过期的查看结果均拒绝。重放将上次次数、错误码和时间加入 `replay_history`，开启新一轮有上限的处理，保留来源与抽取检查点。该命令只重新排队，模型调用仍由调度器执行。显式重放可能产生新的平台模型成本。

`SOURCE_CHANGED` / `SOURCE_UNAVAILABLE` 拒绝这种重放，需要先核查来源与未来的纠正方案。工具不改原文、不删除来源摘要、不让已成功的任务重新生成记忆。这样保留 OPEN-01 的纠正边界。
