# 配置与需求执行一致性审查

日期：2026-11-03。对应 INV-05（消费、停止和账本边界）、INV-08（不伪造真实状态）及 DEC-31/32（流式预览与跨模型衔接）。

同日后续：用户确认开始修复，七组问题已完成[源码修复及隔离回归](../deployment/model-parameter-consistency-20261103.md)，尚未部署远程。下文保留修复前审查证据与边界，不代表当前源码仍保留全部缺陷。

范围：当前工作区的后台模型设置、单人 WebSocket、HTTP 模型代理、供应商适配、上下文预算与查看界面；另核对推荐和记忆策略。此次是代码审查，不修改业务代码或远程配置，不代表生产各分支均已触发。既有未提交工作保留，群聊继续暂停。

结论：确认七组配置/行为不一致。根因是参数分别在后台、上下文构建、计费、传输和适配器中解析，缺少一次解析后共用的有效参数。保护限制可以保留，但必须有明确作用域、可见的生效值和一致的执行口径。

## 1. P1：每次输出额度被点数计费硬上限覆盖

- 证据：[credit-billing.service.ts](../../src/server/services/credit-billing.service.ts:39) 默认4,096、硬上限16,384；[resolveMaxOutputTokens](../../src/server/services/credit-billing.service.ts:109) 取最小值；[credit-generation.ts](../../src/server/services/credit-generation.ts:36) 仅点数模式执行该限制。
- 触发：后台把“每次输出额度”保存为128,000，点数模式下 WebSocket 最终只发送16,384；订阅模式则不经过这一钳制。同一模型配置随计费模式改变行为。无限点数仅跳过余额不足判断，不跳过输出钳制。
- 可见差异：[后台表格](../../src/client/pages/admin/ModelManagement.vue:294) 展示配置值，没有同步解释最终有效值与钳制原因。此前修复移除了错误的4,096覆盖，这层16,384限制仍存在。
- 建议：把模型能力、管理员单次策略、计费保护分别建模；显示有效输出额度与限制来源，计费按同一有效额度冻结。是否提高现有硬上限是产品/运维策略，不能用直接删保护代替一致性修复。

## 2. P1：上下文预留与实际输出额度不同，提前丢历史或拒绝请求

- 证据：[context-manager.service.ts](../../src/server/services/context-manager.service.ts:53) 使用原始模型元数据预留输出；[context-budget.ts](../../src/server/services/context-budget.ts:27) 默认按该输出计算可用输入；[websocket.ts](../../src/server/routes/websocket.ts:661) 先检查上下文，到[后续预扣](../../src/server/routes/websocket.ts:711)才解析计费有效额度。
- 隔离复现：总窗口200,000、配置输出128,000、安全缓冲100时，输入上限按71,900计算；点数模式实际输出16,384时，同一公式允许183,516输入。100,000输入在前一种口径被拒绝，在后一种通过。
- 影响：固定提示词可能被过早拒绝；历史选择可能提前截短。此处不是要求忽略独立输入上限，而是要求使用本轮实际输出额度计算同一个预算。
- 建议：在构建上下文之前解析有效生成参数，供历史选择、最终校验、预扣和供应商请求共同使用。

## 3. P2：特定 Ollama 模型的流式适配写死容量

- 证据：[llm.service.ts](../../src/server/services/llm.service.ts:290) 在 Ollama、上游模型名包含 `qwen3.5`、地址包含 `11434` 时切换原生接口，并写死 `num_ctx: 16384`、`num_predict: 4096`、`think: false`。
- 隔离复现：传入 `max_tokens: 10000`，模拟 fetch 捕获的请求仍为4,096输出与16,384上下文。普通非流式聊天没有这段特例。
- 影响：保存参数、预扣与实际请求不同；小额配置也可能被抬高。仅在上述适配分支触发，不能据此解释当前远程 GLM 的所有问题。
- 建议：原生参数从本轮有效设置转换，推理开关单独配置，普通/流式遵循相同参数语义。

## 4. P2：非默认提示模板保留固定输出、整段返回和不完整取消链路

- 证据：[websocket.ts](../../src/server/routes/websocket.ts:678) 对非默认模板固定预留2,048；[streamTextCompletion](../../src/server/routes/websocket.ts:1297) 固定发送2,048且 `stream: false`，仅请求开始前检查取消；[completion](../../src/server/services/llm.service.ts:348) 没有接收取消选项，OpenAI兼容 fetch 没有传 signal。
- 触发：角色卡扩展选择非默认 `promptTemplate`。管理员输出10,000时仍只有2,048；配置小于2,048时，该分支又可能请求超出管理员额度的输出。单人直接回复须等整段完成才展示，停止也无法通过这条调用链取消在途上游请求。
- 影响：同一页面切换卡片/模板后，输出额度、首字体验与停止行为改变。兼容补全还使用默认重试包装，5xx可能再次请求。
- 边界：固定模板是已有历史实现，前轮输出修复明确未覆盖；不能把它算成前轮已修复，也不能将用户取消等同于已提交状态。本项指出的是上游传输取消缺口。
- 建议：模板参与统一参数解析；支持流式的协议实际流式返回，不支持时明确告知；信号贯穿请求和重试等待。普通状态校验与失败不提交规则保持。

## 5. P2：上下文界面展示演示数据，容量估算也不等于后端实际上下文

- 证据：[ChatWindow.vue](../../src/client/components/chat/ChatWindow.vue:82) 的阅读设置连接上下文查看入口，并[挂载真实对话弹窗](../../src/client/components/chat/ChatWindow.vue:592)；[ContextViewer.vue](../../src/client/components/chat/ContextViewer.vue:196) 的 API 未实现，返回固定 Alice 对话、55 token、128,000窗口与旧模型名，界面没有演示标记。
- 同时：[ChatTokenCounter.vue](../../src/client/components/chat/ChatTokenCounter.vue:239) 固定预留4,096输出；世界书列表是空占位，历史计数为前端加载消息而非后端选入上下文的消息。
- 影响：用户切模型后看不到真实预算；可能把未进入模型的消息理解成已发送，或误判世界书/记忆是否参与。这违反真实数据与演示数据分开的要求。
- 建议：查看器读取经过授权和脱敏的真实上下文诊断；未接入时显示不可用，不能冒充当前会话。前端估算明确标注估算范围，并显示后端有效参数及截断信息。

## 6. P2：示例环境变量中的超时与重试设置未接入

- 证据：[.env.example](../../.env.example:152) 提供 `LLM_REQUEST_TIMEOUT_MS` 和 `LLM_MAX_RETRIES`；源码搜索仅此处出现变量名。[llm.service.ts](../../src/server/services/llm.service.ts:161) 固定最大尝试次数3；[重试循环](../../src/server/services/llm.service.ts:447) 使用该值，流式 fetch 只有调用方 signal，没有绑定这里声明的请求期限。
- 隔离复现：设置 `LLM_MAX_RETRIES=1`，模拟兼容补全接口始终返回500，仍发生三次 fetch。这里的3是最多总尝试次数，并非首次之外再试三次。
- 影响：运维修改示例变量不能得到预期行为；120秒也没有成为这条链路统一执行的应用层期限。底层网络仍可能有自身超时，不能表述为永不超时。
- 建议：将配置接入校验和运行时，统一普通/流式/模板请求的期限与取消；明确“尝试次数”和“额外重试次数”的含义，不支持的变量从示例移除。

## 7. P2：HTTP 模型代理与聊天页面的配置作用域不一致

- 证据：[llm.ts](../../src/server/routes/llm.ts:50) 流式及[普通代理](../../src/server/routes/llm.ts:128) 直接用请求的 `max_tokens` 预扣，没有按后台模型元数据解析默认额度和能力上限。
- 触发：HTTP请求不带 `max_tokens` 时，点数模式回落到4,096，订阅模式原样透传给上游；WebSocket则读取后台每次输出设置。显式 HTTP 参数也不在路由层按该模型能力校验。
- 影响：管理员以为修改了全平台默认值，实际只改变部分入口；请求也可能因超出声明能力而被供应商拒绝。现有 HTTP 测试明确保留订阅模式原样透传，因此这也是作用域契约未统一的问题。
- 建议：明确后台“每次输出额度”是默认值还是强制策略，允许客户端覆盖哪些字段；物理能力仍统一校验，响应/诊断返回最终生效参数。不能简单把所有客户端覆盖都判为错误。

## 已排除与保留的边界

- 同名模型跨渠道误选：后台保存已拒绝跨渠道重名，并要求使用别名；本轮渠道测试通过，不作为普通后台配置缺陷。
- 每轮推荐仍有已完成轮次的生成/回退路径；中断轮次不发布已确认推荐是现行完整性保护，本轮未发现与上述参数覆盖同类的确定缺陷。语义质量不由源码检查证明。
- 自动记忆的抽取阈值、独立生成额度与保留数量已有专门策略。无限点数不等于无限记忆存储；没有把这些独立限制直接算作新增缺陷，也未进行真实多轮记忆验收。
- 未恢复群聊开发、未重放失败轮次、未放松剧情结构校验或失败不提交要求。
