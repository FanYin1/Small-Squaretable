>
> 最后修订：2026-10-18

---

## 一句话定位

**一个更简单的 SillyTavern，面向小圈子商业化运营。**

用户登录网站 → 从社区商城挑一张角色卡（或自己上传）→ 选模型做简单配置 → 开始对话。

不是公开 SaaS，不是 Character.AI 竞品，不是企业级多租户平台。

---

## 目标用户

**小圈子**：几十到低百量级的用户，运营者认识他们或与他们同处一个社群（群聊 / 论坛）。

这个前提推导出后面几乎所有决策，所以单独写明：

- 运营者认识用户 → 不需要内容审核流水线，审核就是运营者手动删卡
- 用户数可控 → 平台统一出 LLM key 在经济上成立
- 社交关系已经在群里 → 站内再建一套关注/动态/评论是重复建设
- 规模小 → 任何需要统计显著性的东西（A/B 实验、协同过滤推荐）都不可能有意义

**这个前提必须由代码保证，而不是靠运气。** 决定：**邀请码注册**。现状是开放注册（代码里没有邀请码，也没有关闭注册的开关）。开放注册 + 平台出推理费 + 放开 NSFW，等于成本可以被任何人刷，上面四条推论也全部不成立。所以邀请码是定位的承重墙，排在 P0（见 `backlog.md` 的 P0-6）。

这是唯一需要做到无可挑剔的路径。不在这条路上的功能，默认不做或下线。

| 步骤 | 现状 |

## 商业模式：预付点数，不是包月订阅

**决定：改为充值点数制。**

现状是 Stripe 包月订阅（free / pro / team），配额写在 `src/server/services/feature.service.ts`：

| 套餐 | messages | llm_tokens |
|---|---|---|
| free | 100 | 50,000 |
| pro | 10,000 | 1,000,000 |
| team | 100,000 | 10,000,000 |

**为什么要换：**

1. 包月 + 平台付推理成本，两头都难受——重度用户亏钱，轻度用户觉得不值。
2. 预付制下成本与收入天然对齐，没有无上限的成本暴露。
3. 小圈子的信任关系本来就适合充值。
4. 最关键的一点：点数制把「上下文深度」变成用户自己的权衡。开长记忆、挂厚世界书就扣得快，用户自己决定要不要。这比替他们设一个 `messages: 100` 的硬配额既优雅也诚实。

**实施约束：**

- 点数按 token 扣，不按消息条数扣。每条消息的成本 ≈ context tokens × 输入单价，context 大小是唯一的主变量，输出占比小到可忽略。
- **必须先修计费口径**（见 `backlog.md` 的 P0-1）。当前主聊天通道只记输出 token，不记输入，而成本的 90%+ 在输入侧。在这个数据上定价等于定在假数字上。
- 界面上要让用户看见扣费（"这条消息用了 6,200 tokens / 0.6 点"）。预付制里这是信任基础，而且它会自然教育用户为什么长记忆值钱。
- `src/server/services/entitlement.ts` 里那套 past_due 宽限期 / 退款吊销逻辑写得很扎实，但充值制下大部分用不上。保留代码，不再是主路径。
- **第一阶段：运营者手动充值。** 用户在群里转账，运营者在后台给账号加点。小圈子的信任关系让这完全可行，而且绕开了支付通道选型这个卡点——支付通道取决于圈子所在地区，Stripe 不一定合适，留到第二阶段再定。
- 充值之前要先定规则：点数是否过期、能否退款。规则写进用户可见的页面，不要只存在于运营者脑子里。

**另一个成本杠杆：前缀缓存。** 成本的大头在输入侧，而输入里角色卡、世界书、历史消息在相邻两轮之间大部分不变——这正是各家 provider 的 prompt caching 打折的部分。但当前的拼装顺序把每轮都变的记忆与情绪放在历史之前，历史永远命中不了缓存。调整顺序可能比任何定价调整都省钱，但会改变模型的表现，需要实测（见 `backlog.md` 的 P3-3）。

## 三个曾经的难题，两个因定位而消失

分析阶段识别出三个硬问题。小圈子定位改变了其中两个的性质：

**1. NSFW 合规 —— 不再是平台的问题。**
运营者认识用户，内容政策变成运营者自己的决定，而不是应付公开平台审核与应用商店规则。

- 保留注册时的 18 岁声明（`src/db/migrations/0036_age_confirmation.sql`）。它恰好是小圈子商业化最需要的那种"已尽告知义务"的证据。
- **决定：NSFW 改为平台开关，默认开。** 现状是硬编码排除——发现入口一律过滤（提交 `7719ac0`）、发布时直接拒绝（提交 `7feca98`）。改为开关后由运营者决定。
- 默认开的前提是两道门都在：**邀请码**（只有运营者认识的人能进来）+ **18 岁声明**（进来的人已声明成年）。邀请码没上线之前，开关不能打开。
- 卡片上的 NSFW 标记保留——平台允许不等于每个用户都想看，标记是用户侧筛选的依据。

**2. BYO-key —— 从「最大架构缺口」降级为可选。**
公开 SaaS 下用户自带 key 是必需的；小圈子下平台统一出 key 反而更好：能批量拿到更好价格，用户不用自己折腾。而"免配 API"正是"更简单的 ST"的核心卖点——ST 最烦的一步就是配 key。

**3. 计费口径 —— 反而变得更要紧。**
因为现在确定是平台在付这笔钱。详见 P0-1。

## 明确不做的事

**这是本文最重要的一节。** 下面每一项都已经有代码，列在这里是为了记录"决定让它下线"以及理由——否则它们会自己长回来。

处置分三档：
- **封存** = 代码留在仓库，路由与前端入口下线，不再维护
- **下线** = 入口关闭，后续评估是否删除
- **简化** = 保留能力，砍掉流程与界面

| 模块 | 行数 | 处置 | 理由 |
|---|---|---|---|
| Flink + ClickHouse 管线 | 4,193 | 封存 | 三个有状态服务的运维负担，换不来小圈子需要的任何答案。PMF 前 Postgres + 物化视图足够 |
| analytics + 实验 + Kafka | 2,343 | 封存 | 几十个用户做 A/B 在统计上没有意义 |
| social：关注 + 动态流 | 4,054（含下行保留部分） | 下线 | 小圈子的人际关系已经在群里，站内关注与动态是重复建设 |
| social：收藏 + 评论 | （同上） | **保留** | 收藏是挑卡旅程的一部分（"我常聊的卡"）；评论是卡片作者在站内获得反馈的唯一途径 |
| 通知 | （同上） | 收窄 | 只保留评论回复、被收藏这类与卡片相关的类型；`follow` 类型随关注下线 |
| admin 后台（6 页） | 2,400 | 简化为 1 页 | 需要的是"删卡 / 封号"两个按钮，不是审核工作流 |
| 插件沙箱 | 1,739 | 封存 | 没人会给几十人的平台写插件 |
| Webhook + 开发者 API | 1,547 | 封存 | 没有第三方集成方 |
| GDPR + 同意 + 审计 | 1,093 | 保留删号与审计日志，同意管理界面下线 | 账号删除真有用。**审计日志不能下线**：年龄声明的举证（`auth.service.ts`）、订阅与退款（`subscription.service.ts`）、管理员操作都在调 `auditService.log`，充值与扣费也要靠它 |
| MFA + TOTP + 备份码 | 1,028 | 降级为可选 | 不要拦在注册路径上 |
| 审核 + 举报 | 805 | 简化 | 运营者认识所有人，审核 = 手动删卡。NSFW 拦截改为开关（见上文） |
| 推荐引擎 | 494 | 下线 | 200 张卡片，排序 + 标签 + 搜索胜过任何协同过滤 |

合计上限约 **19,700 行**对应的入口下线；social 保留收藏与评论、审计日志保留之后，实际略少。

**多租户是明确的例外：不要拆。** 它织进了十几个中间件（`src/server/middleware/tenant.ts` 等），是承重的且无害。只要永远不在界面上暴露它。

**保留为产品本体的部分：**

| 模块 | 行数 |
|---|---|
| chat + websocket + llm + context | 15,752 |
| character + ST 导入 | 10,821 |
| worldbook | 2,156 |
| memory + emotion + embedding | 1,987 |
| preset + override | 1,056 |
| 收藏 + 评论（social 的一部分） | — |
| 审计日志 | — |

## 旅程上真正缺的五样

0. **邀请码注册** —— 定位的承重墙，见「目标用户」。邮箱注册与 OAuth 两条建号路径（`auth.service.ts`、`oauth.service.ts`）都要过这道门。
1. **onboarding** —— 全站零（grep `onboard` / `firstRun` / `tutorial` 无命中）。简化后页面变少，但"第一次进来该干什么"仍需有人告知。
2. **移动端** —— `CLAUDE.md` 声称有 PWA，但 `vite.config.ts` 无 `VitePWA`、`package.json` 无 `vite-plugin-pwa`，**PWA 并不存在**。`ChatWindow.vue` 1985 行只有 1 条 `@media`。聊天产品移动占比大概率过半。
3. **预付点数系统** —— 现状是 Stripe 包月。第一阶段做运营者手动充值。
4. **模型选择的收敛** —— 现状是 provider × 模型矩阵。需要 3–5 个精选项 + 一句人话（"便宜耐聊 / 聪明但贵 / 记性最好"）。用户不该看见 `dolphin-mistral:7b-v2.8-q4_K_M` 这种字符串。
