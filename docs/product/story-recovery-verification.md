## 验证方式

`npm run check:exploration-recovery` 构建当前前后端，使用一次性PostgreSQL/Redis、真实API与WebSocket服务、Chromium以及明确标识的本地受控模型。复用已有数据库并发检查及生成/结算smoke；不会连接3080/3081数据库或真实模型。

新增的浏览器检查使用WebSocket转发拦截故障：请求仍交给真实服务端处理，仅丢弃指定的提交确认、延迟另一标签的消息或中途断开连接。没有用伪造的成功响应替代真实提交。判断依据包含服务端状态、事件、消息、生成请求、费用流水、模型调用数及页面结果。

| 场景 | 验收条件 |
|---|---|
| 正文/状态已经提交，完成确认丢失 | 自动重连后读取已保存正文与状态；一轮仅一次模型调用、一次扣费、一个事件；预扣释放 |
| 重连后显式重放原请求 | 返回已接收提示；状态、事件、消息、费用和模型调用数不变 |
| 第二标签持有过期行动版本 | 拒绝发生在生成和扣费之前；保留草稿、不提供旧版本直接重试，显示最新可选行动 |
| 用户重新确认当前版本行动 | 新请求使用最新版本，仅推进一次；刷新可恢复，另一存档保持原样 |
| 生成中途断线，重连时仍在生成 | 不自动重复发送；最终页面读取完整已保存正文，不能只拼接断线前后的片段 |

限流属于真实环境行为。首轮浏览器运行暴露测试请求过密，随后按实际响应中的限流窗口安排检查节奏，并断言没有429或服务端5xx；未放宽或关闭服务端限流。

## 本轮修复

新增回归复现了生成中途重连时缺少中间文字的问题：数据库保存了完整回复，但页面在完成通知到达时直接采用了本地残缺流式内容。

现在，对经历断线恢复的生成，在结束通知之后重新读取最后一条已保存消息并按消息ID合并，更新页面正文，不重新执行行动。读取失败会明确提示重新打开故事核对，不提供重新生成按钮；迟到的失败不会污染已经切换到的另一故事。
