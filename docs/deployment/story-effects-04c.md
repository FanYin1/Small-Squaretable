# EXP-04C：旧变量事务与多人故障恢复

## 本次开发后的实际效果

1. 旧故事完整回复中的ERA插入、编辑、删除与正文在同一个数据库事务提交。写入失败整体回滚；同一WebSocket请求/人物的提交重放返回原消息，不重复改变量。数据首次从仍可读取的旧Redis变量导入，之后不受该缓存过期影响。
2. 多人回复明确区分已经完成的人物与后续失败或停止的人物。前一人的已确认变化保留，后一人的未完成片段不改变变量、不生成助手派生后果；派生情绪失败不会阻止后续人物回复。
3. 丢失完成通知、断流或另一标签发起对话时，页面按原输入补齐整轮回复并排序；不会只恢复最后一人的正文，也不会把两人的流式文字拼在一起。超过50条缺失消息时继续分页读取；读取失败提示核对，不伪装恢复成功或自动重新生成。
4. HTTP开场白也遵守新旧故事隔离，新快照故事不执行ERA旧变量写入或持久化提示词宏写入。旧变量刷新失败保留当前显示，不把错误伪装成空背包。
5. 原生行动继续保留过期版本拒绝、草稿保留与明确重新确认；这不是新的纠正或分支机制。

新增数据库检查直接注入消息写入、派生写入和Redis读取故障，并检查事务回滚、重复提交、并发增量、级联删除、释放预扣与原请求不重复计费。多人第二次生成已消耗但正文保存失败时，仍结算已消耗部分；费用不冒充剧情资源。

检查过程中的测试工具问题单独记录：最初以降级新快照模拟旧档，被数据库不可变约束拒绝，改为建立真正的旧档结构；另修正变量API包装读取、同一测试加载器的Redis连接清理，以及浏览器请求的限流窗口安排。无效运行没有计入最终通过数，没有放宽产品限流或修改已确认状态来让测试通过。

## 数据与回滚边界

- beta0010 / 正常0050仅新增 `legacy_chat_variables`，不改写旧消息、原生事件、角色快照或已有记忆。第一次访问旧变量时迁入尚在Redis中的值；尚未访问的旧档仍依赖原缓存，已过期且无备份的历史不能凭空恢复。
- 新表随存档删除级联清理，后续数据库备份应包含它。旧Redis副本不再是已经迁入数据库的存档的权威状态。
- 已开始产生新变量数据后，不能仅切回只读Redis的旧应用继续服务。回滚需先核对数据库变量与Redis的转换，或使用理解新表的修复版本；不能直接丢弃新表或倒回数据库来掩盖差异。
- 作者提示词中的旧宏和用户全局变量沿用既有兼容语义；本轮没有承诺任意第三方脚本框架、全局变量或所有提示词副作用的统一事务。
- 请求标识与生成费用边界继续见 [生成请求持久化](generation-requests.md)：无标识的旧HTTP正文写入本轮获得事务保护，不承诺自动识别任意跨请求重复提交；模型消费与正文/变量也不是一个跨供应商事务。
- 真实模型语义质量、自由行动、人物知情、历史纠正、用户视觉与真机签收继续按原任务跟踪。新增付费调用0，累计授权剩余仍为6,681 token。
