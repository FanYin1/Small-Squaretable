## 定位到的阻塞与修复

1. 生产缺少工程请求归属到预算入口的路径。新增服务器管理员配置文件 `ENGINEERING_STORY_ROUTE_FILE`：限定一个 chatId、userId、tenantId、model 和有效期；实时核对所属账户，仅替换该故事的供应商地址与认证。普通故事、无故事上下文的请求仍使用原配置。到期、模型/所属账户不匹配、网关不可用时不会回退至未计量直连。限定故事的非流式调用最多一次尝试。
2. 记忆 worker 原先未将 job 的 chatId 传递至 LLM 服务，现在传递持久 job 的故事上下文，使未来本测试故事的抽取也进入同一预算路径；未暂停正常记忆任务。配置来源只有管理员文件，不开放 HTTP/WS 客户端指定网关能力。
3. 远端没有 ML 服务。迁移队列中已存在 5 条 `EMBEDDING_FAILED` 重试记录，但不能仅根据这些历史记录断言是远端新产生的失败。新增仅内网可见的真实向量容器；离线使用既有多语 MiniLM 缓存，没有替换模型或伪造向量。此次配置为 embedding-only，情绪模型未启用，对应端点明确返回 503。
4. 原应用镜像使用 `npm ci --ignore-scripts`，其 sharp 原生依赖缺失，初次 ML 启动失败。现场镜像补入与锁定版本相符的 Linux x64 原生模块及库。仓库独立 ML Dockerfile 更新 Node 22、保留依赖安装脚本、修正模型缓存位置与 healthcheck（原 healthcheck 依赖未安装的 curl）。现场派生镜像和独立 Dockerfile 构建路径分别记录，不能冒称本轮已测试独立 Dockerfile 完整在线重建。
5. ML 初次 600 MiB 限制导致 OOM，保留失败；本机同模型实测峰值 833,100 KiB，远端提高至 1000 MiB、CPU 限定 1 核后真实计算通过，稳定时约 373 MiB，最终无 OOM/重启。没有为测试停止应用或数据库。
6. 工程账户仅有 10 点，首轮按完整请求需预扣约 20.5 点，生成前返回 `INSUFFICIENT_CREDITS`。为执行用户授权的工程测试，通过追加式点数账本增加 500,000 token（50 点）测试额度并写审计，未设无限权限、未修改凡音、未扩大付费工程总预算。这是工程测试额度，不是实际充值订单。

源码验证：路由隔离、LLM 与记忆边界共 39 项通过；类型检查、服务端构建、ML 脚本语法检查通过。ML 的真实容器推理单列于上表。尚未验证生产自动抽取落库和下一轮召回。
