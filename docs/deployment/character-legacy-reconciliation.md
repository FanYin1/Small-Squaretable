# 历史角色资料：来源选择与差异恢复

2026-10-25。EXP-03B-LEGACY工程交付，原要求映射见[工作包](../product/character-legacy-reconciliation.md)。工具面向持有数据库权限的管理员；本轮未对3081的真实角色、绑定或聊天执行修复，没有新增付费模型验证。

## 实际效果

此前补建工具只接受“当前有效内嵌书且完全无绑定”。现在可以明确选择当前书、旧包装书、原始归档书，或者提供原角色PNG/JSON、独立书JSON，为指定角色恢复一份绑定资料。对已有编辑、重复或停用的书，先列出全部绑定的keep/detach处置；也可明确选用某一本已有书，并在预览中确认启用和角色作用域。

恢复来源时创建新副本，保留原角色数据与原书条目。选择已有书时不改条目正文；解绑只移除角色关联并设为character作用域，防止原global绑定在解绑后意外全局生效。未选中的停用书保持停用，不能把重复或停用直接当作损坏。原型、网页和3081镜像没有因这项管理员工具而改变。

权限冲突、找不到来源、缺少绑定处置、归档内部来源冲突、资料超限，以及目标参与无冻结快照的旧聊天时，整个操作拒绝。此工具不会猜测历史意图、迁移所有权、自动升级旧聊天或生成不存在的世界观。

## 操作与复核

先由运维人员在进程环境中明确设置目标`DATABASE_URL`；工具不读取任何`.env`文件。应用前备份数据库，并将请求、计划、回执和相邻`.source`原件纳入受控备份；原件可能包含完整角色卡，不应放入公开文档。

请求JSON例子（UUID须替换为已核对的真实范围）：

```json
{
  "tenantId": "10000000-0000-4000-8000-000000000001",
  "ownerId": "20000000-0000-4000-8000-000000000002",
  "characterId": "30000000-0000-4000-8000-000000000003",
  "source": { "kind": "archive" },
  "bindings": [
    { "bookId": "40000000-0000-4000-8000-000000000004", "action": "detach" }
  ]
}
```

`source.kind`可为`current`、`nested`、`archive`、`file`或`bound`。前三项准确指向当前顶层、旧data包装、`_squaretableImport.version=1`原件中的书；不会按优先级猜选。`bound`还必须提供`bookId`，且该书在bindings中选择keep；预览会明确标为activate。bindings必须完整包含当前所有绑定，没有绑定则传空数组。不能选择其他角色或其他所有者的书。

```sh
node --import tsx scripts/character-legacy-reconcile.ts \
  --mode plan --request /受控目录/request.json \
  --report /受控目录/plan.json

node --import tsx scripts/character-legacy-reconcile.ts \
  --mode apply --plan /受控目录/plan.json \
  --expected-plan '<复核后的plan.fingerprint>' \
  --report /受控目录/applied.json
```

选择file时，plan与apply均须增加`--source-file /受控目录/原文件`。每次成功报告旁都会保存同字节的`报告路径.source`原件，0600且只允许新建。可直接将`plan.json.source`用于apply；不会按文件名或人物名搜索其他资料。普通原文件、计划与请求均禁止符号链接输入；原件限制10 MiB，请求/计划限制64 KiB。PNG解析和独立书字段映射复用既有导入实现，不执行作者脚本。

计划仅包含范围ID、来源摘要、当前审计摘要、目标条目数和逐本绑定的作用域/启用/数量/内容摘要及差异字段名，不包含名称、正文、关键词、路径或对话。差异字段比较每个字段的值集合，不是按条目历史ID推断出的逐行合并方案。计划指纹覆盖整个请求和预览；它是复核和幂等依据，不是来源真实性签名或数据库访问授权。

plan事务只读，不能把退出码0视为已经修复。apply必须使用原计划和明确指纹，复核后有任何来源、绑定或条目变化都拒绝。报告`applied`才表示本次提交成功；`already_applied`表示过去已提交，`currentStateRechecked=false`，不证明当前仍完整，也不会复活后来删除的书。

## 提交结果未知与回执

将仅含tenantId/ownerId/characterId的范围写入scope.json，使用原计划指纹查询：

```sh
node --import tsx scripts/character-legacy-reconcile.ts \
  --mode receipt --scope /受控目录/scope.json \
  --expected-plan '<原计划指纹>' \
  --report /受控目录/receipt.json
```

receipt不需要原件或计划文件，仅读取持久凭据。`already_applied`返回原书ID、条目数和提交时间；`not_applied`表示在该次查询快照中没有此凭据，不能排除另一进程仍在提交。等待进行中的操作结束后，可用相同计划重试；不要换计划盲目重复补建。提交后输出故障仍可能已经写入数据库，工具统一提示按原指纹核对。

回执复用`character_import_repairs`表，使用包含`character-legacy-v1`命名空间的完整计划摘要作为键；不新增迁移，既有窄范围补建工具继续使用原协议。书删除不会删除回执；角色被删除会按原表外键删除该角色凭据，不承诺删卡后仍可重查。原书/条目保留可供复核；撤销需另做明确的绑定计划或恢复备份，不能把重新运行旧计划当作撤销。

## 事务、存档和限制

apply依次锁定角色、按ID排序的绑定书和条目，等待后重新读取全部状态。角色锁与网页绑定的共享锁及外键协调；书排他锁阻止检查期间插入条目的幻读，条目锁阻止编辑/删除。重复提交先查持久回执，复制、解绑/启用和凭据写入在同一事务内完成。语句15秒、锁10秒超时。

读取沿用12 MiB卡资料、50本绑定书、10,000条条目及32 MiB书/条目审计边界。拒绝造成后续绑定数或条目数超过该数量边界的复制。工具只更新供以后开局使用的资料；已有版本1内容/世界书快照保持原样。参与任一未冻结单人或多人旧聊天的角色整体拒绝，须先另行处理旧档产品语义；不以本工具伪装完成旧故事升级。

恢复后原角色的旧包装/归档和当前内嵌字段不会被改写，旧审计仍可能报告archive_source_only或bound_content_differs；这可能是本次显式选择的正常结果，应结合计划与回执判断，不能再次据此自动补书。外部原文件的未知扩展保存在相邻`.source`中，数据库仅保存共享映射支持的运行字段；数据库备份不包含这些外部文件，必须单独备份。
