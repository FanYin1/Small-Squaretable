# 开局身份快照：实现与隔离验证

记录日期：2026-10-23（UTC+8）。工作包 EXP-04A 的身份子项，关联 DEC-07、08 / INV-01、03、09；任务状态仍以 [活动待办](../product/backlog.md) 为准，EXP-04A 保持未完成。

本次解决的是：玩家修改或删除人设后，旧故事的称呼和生成提示原本会跟着改变。现在标准创建接口在建档时保存身份，旧故事继续使用原身份，同卡另开才读取当前身份。此项是存档连续性的基础，不等于完整记忆系统或通用作者身份协议。

## 1. 用户可见行为

| 场景 | 当前行为与依据 |
|---|---|
| 使用选定人设开始 | 保存该人设当时的称呼与描述，阅读标题、开场宏与生成提示使用同一份快照 |
| 未指定人设开始 | 保存账户当时的显示名称；没有显示名称时沿用既有 `User` 缺省值 |
| 开局后修改人设或账户名称 | 已建立的故事保持原身份；同卡另开读取修改后的资料 |
| 删除来源人设 | 人设外键可置空，故事仍保存原称呼、描述与来源标识 |
| 创建成功但响应丢失 | 同一请求恢复原存档及原身份，不重新捕获后来修改的人设 |
| 进入旧存档 | `identitySnapshot = null`，保留旧有实时人设/账户行为，不猜测历史身份或静默补写 |
| 阅读设置 | 明确说明本次身份已固定，或此旧档仍使用当前身份资料 |

只持久化本次选择的玩家身份。作者固定身份、可选身份限制及冲突提示尚未接通；不得把快照保存理解成作者约束已验证。旧阅读页的探索行动、资料面板、地图也未因此完成。

## 2. 数据与调用链

- `src/types/story-identity.ts` 定义协议 1：归属用户/租户、账户或人设来源、来源 ID、称呼、描述、内容 SHA-256 与捕获时间。SHA-256 是内容摘要，不是数字签名或完整性鉴权机制。
- `src/server/services/story-identity.service.ts` 在事务内核对账户及人设归属，从数据库读取资料；不接受前端自报的快照内容。
- `src/server/services/chat-creation.service.ts` 将请求占位、身份快照、存档与参与角色一起提交。已有请求重放直接读取原档，不覆盖快照。
- 标准 `POST /chats` 的有请求标识和无请求标识两条入口都使用此事务；无标识时服务端生成随机标识，每次请求仍为一次新建，不承诺客户端重复请求去重。
- 既有存档读取接口返回 `identitySnapshot`。前端校验格式和归属，未知协议/坏快照不会静默伪装成旧档；固定身份不再请求来源人设。增强提示和 HTTP 回退提示均接入快照，服务端保存开场时也使用快照展开称呼宏。
- 快照放在所属 `chats` 行，删除故事时随行删除。既有导出/分享与恢复导入尚未扩展为完整快照归档协议，不声称导入导出后仍能保留该身份。

## 3. 迁移与部署边界

普通迁移新增 `src/db/migrations/0042_story_identity_snapshot.sql`；beta 迁移新增 `src/db/beta-migrations/0002_story_identity_snapshot.sql`。二者用于各自迁移链，不能对同一库把两条链重复应用。

新增可空 `chats.identity_snapshot`，检查非空值为 JSON 对象；数据库触发器禁止在创建后更换快照，也禁止将旧档的空值直接填成一个猜测快照。普通改标题以及删除人设导致的外键清空继续允许。完整结构约束在共享协议和创建路径校验，数据库 CHECK 不替代完整协议校验。

新应用启动前必须应用对应迁移，否则查询新增列会失败。迁移已在一次性数据库验证；**3080 既有 R5 候选及数据库未更新，5188 原型仍保留**。新增列兼容旧应用，但回滚应用后由旧创建路径产生的存档可能仍无快照；不可将回滚镜像等同于回滚数据。后续部署应先备份并核对实际迁移记录。
