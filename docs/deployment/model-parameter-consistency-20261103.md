## 参数的实际含义

- 模型最大输出：供应商能力声明；项目不按型号猜测新的容量。
- 每次输出额度：管理员给模型设置的应用上限，适用于单人 WebSocket、HTTP聊天、模板和服务层生成；单次调用可以申请更少，不能通过较大的 `max_tokens` 绕过管理员策略。
- 有效输出：管理员上限、能力声明和单次申请的最小值。缺少单次申请时使用管理员配置；未知模型继续采用既有保守元数据，不能据此宣称已验证供应商容量。
- 每轮先解析并保存容量快照，再用于上下文构建、摘要补入、最终校验、冻结额度和模型请求。管理员在生成期间保存新容量时，已开始轮次使用原快照，后续轮次使用新值。
- 点数计费不再额外压低到16,384；余额检查、输入估算余量、预扣、取消结算和平台预算仍保留。无限余额不等于无限单次输出。冻结计算增加安全整数溢出检查。

例如：窗口200,000、每次输出128,000，仍需为真实可能生成的128,000预留空间，可用输入为71,900。单次合法申请16,384时，可用输入变为183,516；若另有较小的独立输入上限，则继续取该上限。修复不是让输入与输出同时超过总窗口，而是消除“预留128,000、实际只发16,384”的矛盾。

## 七组审查项的处理

| 审查项 | 修复后的行为 |
|---|---|
| 计费输出硬上限 | 移除独立16,384钳制，按已经校验的有效输出冻结；后台说明管理员上限语义 |
| 上下文与请求不一致 | 引入统一参数解析，单人轮次把同一容量快照传到历史选择、摘要、校验与上游 |
| Ollama参数特例 | 普通与流式均按原生协议发送 `num_ctx` / `num_predict`；移除按型号强制关闭思考及写死容量的分支，不新增推理开关 |
| 非默认模板旧链路 | 与普通聊天共用流式解析、正文预览、完成信号、截断保护、实时计量和取消；兼容补全使用格式化 prompt，原生协议按自身格式适配 |
| 演示上下文界面 | 删除固定演示会话与虚构统计，明确显示实际详情暂未接入；文字计数只统计已加载角色和对话，标注为估算，未知容量显示未知 |
| 超时与重试配置无效 | 接入配置校验与Compose传递；期限覆盖请求、响应正文和重试等待，用户取消可中断等待；流式不重放 |
| HTTP与网页配置不同 | HTTP在预扣前解析容量并校验输入；订阅模式也发送有效输出，响应头 `X-LLM-Max-Output-Tokens` 返回本次值 |

模板的实时流由同一完整性解析器处理：兼容文本流的 `choices[].text` 和普通聊天的 `delta.content` 都保留结束原因。缺少终止依据、格式错误、超时、取消和 `length` 不能成为已确认剧情。没有追加自动修复调用或自动重放。

Ollama原生NDJSON在服务层规范化为SSE，携带模型别名、输出、结束原因和实际usage，避免HTTP消费者遗漏用量；断流时不制造成功结束标记。显式配置的Anthropic/Gemini协议继续优先按其协议适配。

HTTP `/completions` 仍只提供普通文本补全：收到 `stream: true` 会在预扣前明确返回400 `STREAMING_ENDPOINT_REQUIRED`，提示改用 `/chat/completions`，不再静默返回普通JSON。角色卡模板在服务内部走流式路径，不受这个HTTP入口限制。供应商若不支持所选协议的流式补全，请求会失败并保持失败不提交；没有付费重试或降级调用来掩盖不支持的能力。

## 运维配置

| 变量 | 默认 | 语义 |
|---|---|---|
| `LLM_REQUEST_TIMEOUT_MS` | 120000 | 一次生成请求的总期限，包含响应正文读取；此前示例值未生效，现在会执行 |
| `LLM_MAX_RETRIES` | 3 | 普通调用最多总尝试次数，包含首次；范围1–10，设1即不自动重试；4xx不重试 |

期限和用户取消取先发生者；队列显式指定较少尝试次数仍有效。流式开始后不自动重放。长输出如果超过请求期限仍可能中断，需要按实际服务能力设置部署期限，不能把128K额度理解为保证输出128K。Compose配置修改需要部署/重启相应应用才会生效；本次远程发布已加入这两个环境变量的传递，并核实运行值分别为120000与3。
